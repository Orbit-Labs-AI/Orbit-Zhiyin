# 这些数字到底在说明什么

当前后端只回答三个问题：哪些要求在记录里出现过，哪里值得回看，有没有适合小范围试用的方法。它还不能预测一个人的长期偏好，也不能证明某个 skill 会改善结果。

## 为什么按会话计数

假设 8 个会话中，有 3 个要求解释更直观。结果就是“3 / 8 个会话出现过这个要求”。同一会话重复强调十次，仍只计一次，避免一次反复修改把画像推得过重。分场景时，分母也只取该场景里有用户消息的会话。

这个比例反映明确要求出现的频率，不是满意率。没提出要求，也可能是任务不需要、用户没说，或者导入器没识别出来。会话也未必独立：同一任务或 fork 可能共享背景。

<details>
<summary>参考区间怎样计算，以及为什么不能直接当成概率</summary>

令每个会话的标记为 `R_i`：出现明确要求取 1，否则取 0。`k = Σ R_i`，`n` 是有效会话数，观察比例为 `p̂ = k / n`。

只有把这些标记近似看成独立、同分布的二项样本时，才有常见的区间解释。代码保留 Wilson 参考区间，默认 `z = 1.96`，计算如下：

```text
denom  = 1 + z²/n
center = (p̂ + z²/(2n)) / denom
half   = z · sqrt(p̂(1-p̂)/n + z²/(4n²)) / denom
interval = [center - half, center + half]
```

例如 `k = 3, n = 8`，得到约 `[13.68%, 69.43%]`。区间很宽，说明即使理想抽样假设成立，这点数据也不足以给出精确推断。当前历史记录既不保证随机抽样，也不保证会话独立，因此这个值只放在开发者数据里作参考，不参与资源排序，更不解释成“用户喜欢这个方法的概率”。`n = 0` 时返回未知。

</details>

## 为什么时间不能直接相加

同一会话里，两次工具记录分别覆盖 0–5 秒、3–8 秒。相加是 10 秒，但 3–5 秒被算了两遍。取区间并集得到 8 秒，也就是每个时刻只算一次。代码先按开始时间排序，再合并重叠区间，复杂度为 `O(m log m)`。

这里得到的是日志记录覆盖的跨度。调用可能包含等待，跨会话也可能并行，所以它不是模型计算时间、你的工作时间，更不能直接变成“浪费了多少时间”的结论。

## 为什么发现卡点后还可能没有推荐

推荐必须同时满足：有明确要求、有对应事件、资源适用于该场景和交付语言，而且来源版本已核对。缺一项就暂不推荐。例如连续三次失败只能形成一个回看候选；如果是预期失败测试，或没有对应协作要求，就不能据此推荐排错方法。

这些条件能说明“值得试”，不能说明“试了必然更好”。后者需要固定同一任务和必要事实，比较使用前后，并让目标读者评价。当前读者材料已具备，真实收益标签仍待收集。

## 原回复、改写与期望怎样联系

当前状态先取日志可观察的部分：任务场景、工作目录、模型、读者与语言要求、待交付限制和所处阶段。用户输入是当前请求；随后观察到的回复、工具状态和反馈是结果。它们不是完整的项目状态，也未证明满足 Markov 假设。

用户希望得到的下一状态 p 不能直接读出来；一次实际结果也不能给出 Agent 的完整分布 q。当前实现先核对明确限制和修改发生位置，再保存同一任务的原回复、改写与相对评价。没有前后正文或明确比较时，缺失值保持未知。

成对偏好方法学习的是“同一情境中，哪一个结果更合意”，需要相对标注。相关研究使用成对的人工偏好数据，而不是把没有追问解释成满意。[Christiano 等的原论文](https://arxiv.org/abs/1706.03741)

<details>
<summary>Bradley–Terry 可以怎样接入，当前为什么还不拟合</summary>

令 x 是任务情境，φ(y) 是回答的可解释特征。一个简单的条件模型为：

```text
P(新版优于旧版 | x) = sigmoid(R(x, 新版) - R(x, 旧版))
R(x, y) = w(x) · φ(y)
sigmoid(t) = 1 / (1 + exp(-t))
```

新版相对评分越高，模型给出的偏好概率越大。Bradley–Terry 的相对评分形式也用于 DPO 的偏好模型推导；它不等于原先的项目状态转移分布 p(s′|s,a)。[DPO 原论文，第 3 节与附录 A.2](https://arxiv.org/html/2305.18290v3)

当前 φ 只记录留存回复的首层字数、标点分段数和平均分段长度，不把更短当作更好；内容与数学条件是否等价仍未核验。相对评价是候选证据，人工标签为空，因此 `preference_weights / learned_preference` 都为空，不拟合 w。

后续训练需要同情境标注、内容核验、相关任务分组和未使用过的测试样本。只按时间分割还可能让同任务或 fork 的内容跨两侧。带正负号的 Accept/Retry 分数也不能直接除以总和当概率，负数不满足概率公理；改成 softmax 只能保证形式合法，不能保证它代表用户期望。

</details>

修改发生在回复之后，支持先检查说明方法；相同参数的连续工具失败，支持先检查定位过程。是否进一步自动触发 hook，需要重复证据、错触成本和效果对照。推荐前后的观察差异也可能来自任务难度或同时发生的其他改动，不能直接当作因果收益。

<details>
<summary>自动对照中的误报与漏报</summary>

每个构造案例独立导入，先运行分析与推荐，再读预先写好的标签。多报的标签计为误报，漏掉的标签计为漏报。精确率是 `TP / (TP + FP)`，召回率是 `TP / (TP + FN)`；分母为零时保留未知，不写成 100%。

去掉画像、瓶颈或场景要求后，推荐应当消失，这是检查条件确实生效。它不能证明这些条件足以产生好的体验。已经用于修规则的案例属于回归集，不能再当作独立验证；读者的空白评分也不能当成认可。

</details>
