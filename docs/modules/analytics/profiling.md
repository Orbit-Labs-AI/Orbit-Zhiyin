# 画像和瓶颈怎样从记录里产生

画像先回答“这批任务中，你明确要求过什么，协作怎样推进”。瓶颈再回答“哪次要求与交付值得一起回看”。这两个结果独立生成，资源目录只在最后参与推荐。

本文前半部分说明 legacy 画像（`profiling/*`，规则版本 `rules-v14`）：它只描述任务场景、协作要求和过程记录，不输出人格类型、自主能力分数、浪费时间或技能收益。App 中的 16 型协作人格由 `uiview.persona`（`uiview-persona-v0`）单独产出，见下文“16 型协作人格”。`analytics.presentation.profile`（`collaboration-profile-v2`）只描述明确请求、任务分布、偏好与趋势，`typing.produces_type_code=false`，不输出四字码。[前端指标](presentation-metrics.md)中的 `collaboration-profile-v1` 与 [UI 分析与验收](analysis-products.md)中的 `type_code=null` 是旧描述，以本文为准。

legacy 规则同时覆盖中文与英文：clarity／brevity／planning／verification／autonomy 各有英文等价短语（如 keep it concise、plan first、run the tests），否定、提问和“讨论某事”语境不计为要求。“术语未解释”按通用形态判断（未定义的大写缩写、下标符号，排除 API／JSON／JS 等常见缩写），不再使用某一篇会话的专有词表；回复开头 500 字内有 3 处即开复核候选，这是复核启发式，未经校准。

## 从一组虚构记录看过程

用户先说“给初学者写一份教程，把思路讲清楚”，收到回复后说“没看懂，换个直观的例子”。

1. 标准化保留角色、轮次、模型、来源类型和行号；界面镜像不重复计数。
2. 上下文模块把后一句识别为同任务的跟进，保留教程场景与读者。
3. 画像记录一次讲解要求和一次修改要求。支持它们的是一个会话、一个任务、两条消息。
4. 瓶颈输出最初要求、回复、后续修改的顺序。这能证明发生过修改，不能证明原回复失败，更不能计算浪费时间。
5. 资源匹配检查同场景的要求、具体事件、资源能力与交付语言；全部满足时才建议试用。没有适用资源，前四步仍完整输出。

这个案例没有指定“说人话”或某个 skill。资源效果也不会因为被推荐就自动记为成功。

## 数字的口径

对要求 d，消息数 m 是不同证据事件的数量；任务数 t 是不同 `(会话, task_id)` 的数量；会话数 k 是出现过要求的不同会话数量。同一任务说十遍，可以增加 m，但不增加 k。任务边界来自明确新主题、短跟进和交付上下文，仍需要抽查。

会话分母 n 是这次范围内有用户输入的会话数，k/n 只描述样本覆盖。画像按覆盖数排列，排序不表示要求的重要程度。场景允许在同一会话内共存，场景会话数不能相加当作总数。

过程统计记录每任务的用户消息数中位数，以及 `(工具调用数 + 非进度回复数) / 用户消息数`。它描述日志密度；消息多可能是补充需求，也可能是纠错，调用多可能是任务复杂，不能直接兑换成低效率或低自主性。没有用户消息时比例为空。

每个瓶颈案卷包括观察、证据顺序、相关要求、缺失材料和未确认事项。文件交付只有链接时，先说明缺正文；不根据“文件已写好”评价文件本身。

## 怎样避免围着 demo 调算法

定义来自可观察的任务要求与过程边界，公开项目用于核对格式、技术和资源能力。新增统计先用虚构的跨任务案例检查，再固定代码版本，之后运行真实样本。匹配条件没有指定目标 skill，也没有为这批真实记录拟合权重或调推荐阈值。

此前已经查看过本地样本，并用它排查过解析问题；不能再把它称为独立测试集。本轮真实数据的角色是展示和运行核对。已有构造案例用于修规则后属于回归检查，中文是否自然、推荐是否有效仍需读者和同任务试用。

## 16 型协作人格（uiview persona）

四轴、单位与信号（`axes[].sig` 只列实际参与计算的信号）：

| 轴 | 单位 | p 的定义 | 区间 |
| --- | --- | --- | --- |
| D 委托 / S 掌舵 | 真人触发的轮次 | 步数 ≥ `step_threshold`（5）的轮次占比 | 按会话聚类 |
| I 即兴 / P 规划 | 每会话首条真人消息 | 无结构开场的占比 | Wilson |
| M 多线 / F 专注 | 活跃日 | 同日 ≥ 2 个 Agent 或会话时间重叠的天数占比 | Wilson |
| V 求证 / T 信任 | 真人触发的轮次 | 要求验证或运行验证命令的轮次占比 | 按会话聚类 |

value = 100·p。区间整体 ≥ 55 取高极字母，≤ 45 取低极字母，否则 `?`（experimental）；单位不足（D/I/V < 30、M < 10）或活跃日 < 10 为 insufficient；整体 < 30 个会话不 `ok`。置信度 `conf` 由定型轴数决定：0 轴为低、1–3 轴为中、4 轴为高，同时输出 `settled_axes`。

同一会话的轮次相关，D/V 不能把轮次当独立样本。实现用比率估计的线性化方差 m/(m−1)·Σ(k_i − p·n_i)²/(Σn_i)²（Cochran 1977，*Sampling Techniques* §6.4）换算 Kish 有效样本量 n_eff = p(1−p)/var，上限为轮次数；会话间方差为 0 时取会话数。再在 n_eff 处取 Wilson 区间。因此同一会话里重复的轮次不会缩窄区间，`axes[].n_eff` 与 `ci_basis` 会写出实际口径。

### 阈值的来源与敏感性

所有门槛集中在 `uiview/persona.py` 的 `CONFIG`：

| 参数 | 值 | 依据 |
| --- | --- | --- |
| `min_sessions` | 30 | 正态近似常用的 n ≥ 30 经验下限；产品默认 |
| `min_days` | 10 | 避免单次集中使用定义习惯；产品默认 |
| `min_units` | D/I/V 30，M 10 | 同上；M 以天为单位，样本天然更少 |
| `band` | 45–55 | 50% 中点两侧各 5 个百分点的不判定带；产品默认，没有人群基线 |
| `step_threshold` | 5 | 来自 `uiview/facts.py`，未按 Agent 的工具粒度标定 |

判定带的敏感性：在有效样本量 n 下，要让 Wilson 下界越过高侧阈值，观测占比至少为

| 判定带 | n = 30 | n = 100 | n = 300 |
| --- | --- | --- | --- |
| 50–50（无带） | 67.9% | 59.9% | 55.7% |
| 45–55（默认） | 72.9% | 64.8% | 60.7% |
| 40–60 | 77.6% | 69.7% | 65.6% |

在仓库合成库（150 会话，`tests/uiview/synth.py`）上，判定带取 50–50、45–55、40–60 时，定型轴都是 I、V，结果为 `?I?V`；D 的区间 44.0–51.3 跨过 50，M 的区间 47.6–72.4 也太宽。合成数据只能说明计算是否稳定，不能代表真实用户的分布。

局限：D 的步数取决于 Agent 的工具调用粒度；I 只看首条消息，续会话会被判为即兴；V 包含 Agent 自行运行的验证命令，不能区分是否由用户要求；M 把同日顺序使用两个 Agent 也算作多线。这些构念问题的修正涉及 `uiview/facts.py`，由事实层负责。

## 在 CLI 中核对

```sh
.venv/bin/tandem demo --output .local/demo
.venv/bin/tandem --db .local/demo/demo.sqlite report --output .local/demo --view profile
.venv/bin/tandem --db .local/demo/demo.sqlite report --output .local/demo --view bottlenecks
.venv/bin/tandem --db .local/demo/demo.sqlite report --output .local/demo --view process
.venv/bin/tandem --db .local/demo/demo.sqlite evidence <报告中的证据ID>
```

同一目录下的 `profile.json / bottlenecks.json / process.json` 保存结构化副产品；对应 Markdown 便于阅读。`analysis.json` 保留完整结果，`report.md` 再解释推荐与下一步。技术模块见 [架构](../../architecture/backend.md)，统计假设见 [建模说明](modeling.md)。
