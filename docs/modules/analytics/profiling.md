# 画像和瓶颈怎样从记录里产生

画像先回答“这批任务中，你明确要求过什么，协作怎样推进”。瓶颈再回答“哪次要求与交付值得一起回看”。这两个结果独立生成，资源目录只在最后参与推荐。

本文前半部分说明 legacy 画像（`profiling/*`，规则版本 `rules-v14`）：它只描述任务场景、协作要求和过程记录，不输出人格类型、自主能力分数、浪费时间或技能收益。App 中的 16 型协作人格由 `uiview.persona`（`uiview-persona-v1`）单独产出，见下文“16 型协作人格”。`analytics.presentation.profile`（`collaboration-profile-v2`）只描述明确请求、任务分布、偏好与趋势，`typing.produces_type_code=false`，不输出四字码。[前端指标](presentation-metrics.md)中的 `collaboration-profile-v1` 与 [UI 分析与验收](analysis-products.md)中的 `type_code=null` 是旧描述，以本文为准。

legacy 规则同时覆盖中文与英文：clarity／brevity／planning／verification／autonomy 各有英文等价短语（如 keep it concise、plan first、run the tests），否定、提问和“讨论某事”语境不计为要求。“术语未解释”按通用形态判断（未定义的大写缩写、下标符号，排除 API／JSON／JS 等常见缩写），不再使用某一篇会话的专有词表；回复开头 500 字内有 3 处即开复核候选，这是复核启发式，未经校准。

## 从一组虚构记录看过程

用户先说“给初学者写一份教程，把思路讲清楚”，收到回复后说“没看懂，换个直观的例子”。

1. 标准化保留角色、轮次、模型、来源类型和行号；界面镜像不重复计数。
2. 上下文模块把后一句识别为同任务的跟进，保留教程场景与读者。
3. 画像记录一次讲解要求和一次修改要求。支持它们的是一个会话、一个任务、两条消息。
4. 瓶颈输出最初要求、回复、后续修改的顺序。这能证明发生过修改，不能证明原回复失败，更不能计算浪费时间。
5. 资源匹配检查同场景的要求、具体事件、资源能力与交付语言；全部满足时才建议试用。没有适用资源，前四步仍完整输出。

这个案例没有指定“说人话”或某个 skill。资源效果也不会因为被推荐就自动记为成功。

## 数字的口径

对要求 d，消息数 m 是不同证据事件的数量；任务数 t 是不同 `(会话, task_id)` 的数量；会话数 k 是出现过要求的不同会话数量。同一任务说十遍，可以增加 m，但不增加 k。任务边界来自明确新主题、短跟进和交付上下文，仍需要抽查。

会话分母 n 是这次范围内有用户输入的会话数，k/n 只描述样本覆盖。画像按覆盖数排列，排序不表示要求的重要程度。场景允许在同一会话内共存，场景会话数不能相加当作总数。

过程统计记录每任务的用户消息数中位数，以及 `(工具调用数 + 非进度回复数) / 用户消息数`。它描述日志密度；消息多可能是补充需求，也可能是纠错，调用多可能是任务复杂，不能直接兑换成低效率或低自主性。没有用户消息时比例为空。

每个瓶颈案卷包括观察、证据顺序、相关要求、缺失材料和未确认事项。文件交付只有链接时，先说明缺正文；不根据“文件已写好”评价文件本身。

## 怎样避免围着 demo 调算法

定义来自可观察的任务要求与过程边界，公开项目用于核对格式、技术和资源能力。新增统计先用虚构的跨任务案例检查，再固定代码版本，之后运行真实样本。匹配条件没有指定目标 skill，也没有为这批真实记录拟合权重或调推荐阈值。

此前已经查看过本地样本，并用它排查过解析问题；不能再把它称为独立测试集。本轮真实数据的角色是展示和运行核对。已有构造案例用于修规则后属于回归检查，中文是否自然、推荐是否有效仍需读者和同任务试用。

## 16 型协作人格（uiview persona）

每个维度综合多个信号（`uiview/persona_signals.py`；前端 `prototypes/advance/src/js/15-derive.js` 的 `PSIG` 为同一份表，示例与 live 共用）。每个信号先经**有界分段线性锚点**映射为 0–100 分（高分 = D / I / M / V 一极；两端是平台，单个极端值拉不动整体），维度值 = 有数据的信号按权重加权平均；某信号没有数据就退出，其余权重重新归一化。`axes[].signals` 列出参与本次计算的信号、权重与分数，`axes[].sig` 只列有数据的信号。

| 轴 | 信号 | 单位 / 类型 | 权重 | 锚点（原始值 → 分数） |
| --- | --- | --- | --- | --- |
| D 委托 / S 掌舵 | 步数 ≥ 5 的轮次占比 | 轮次，比率（按会话聚类） | 0.50 | 0 → 5，1 → 95 |
| | 每会话真人消息数 | 会话，均值 | 0.25 | 1 → 80，3 → 65，8 → 50，20 → 25，50 → 10 |
| | 打断与中止率（轮次以 interrupted / aborted / cancelled / rejected 结束；failed / error 是工具或环境失败，不算） | 已知状态的轮次，比率 | 0.25 | 0 → 65，10% → 50，25% → 25，50% → 8 |
| I 即兴 / P 规划 | 开场未写列表 / 验收标准（含指令层 `execution_order` / `acceptance_criteria`） | 会话，比率 | 0.35 | 0 → 5，1 → 95 |
| | 开场引用规格 / 计划文件（spec、PRD、RFC、`*plan*.md` 等） | 会话，比率 | 0.20 | 0 → 60，15% → 45，40% → 20，100% → 5 |

| | 子代理并行度：同时运行 ≥ 2 个子会话的会话占比 | 会话，比率 | 0.15 | 0 → 40，10% → 55，30% → 75，60% → 92 |
| V 求证 / T 信任 | 用户要求验证或 Agent 运行测试/检查/构建命令的轮次占比 | 轮次，比率（按会话聚类） | 0.70 | 0 → 5，1 → 95 |
| | 回滚与重做：会话里有 `git revert` / `git reset --hard` / `git restore`（只带 `--staged` 的取消暂存不算）/ `git checkout -- <path>`（`git -C <dir>` 等全局选项先跳过），或不超过 400 字的真人消息要求回滚 / 撤销 / 重做 | 会话，比率 | 0.30 | 0 → 40，10% → 60，25% → 80，50% → 95 |

锚点依据（产品默认，未在人群数据上拟合）：占比型主信号（每轴第一行）保持旧版 value = 100·p 的口径，只压到 5–95，50% 仍是分界；其余信号把「没有这种行为」放在中性附近（例如没有规格引用记 60、没有回滚记 40、没有子代理记 40），因为缺少某种行为只是弱证据，不能单独决定字母；每会话 8 条消息、首条消息约 130 字、日均 3 个会话分别是 D、I、M 分数 50 的位置，取自 v0 的经验分界（旧 D 公式以「自主比 8」为中点、旧开场规则以 200 字为结构化阈值）。权重让每轴的主信号占最大份额（0.35–0.70），新信号合计不少于 0.30，以保证弹窗列出的信号都能实际改变结果。

字母只看取值：value ≥ 50 取高极字母，< 50 取低极字母；没有任何信号的轴按 50 计（state 为 `no_data`）。1 个会话即可给出完整的 4 字母类型，只有空选择没有画像。区间：比率信号在下文的聚类有效样本量处取 Wilson 区间并经同一锚点映射，均值信号取 均值 ± 1.96·sd/√m（只有 1 个单位时 ±1.96·25），维度区间按权重合成（假定信号独立）。区间整体落在 45–55 之外的轴标 `decided`。

置信度 `conf` 同时看会话数与信号一致性：会话数 ≥ 100 为高、≥ 30 为中、其余为低；`consistency` = 各轴「与维度同侧的信号权重占比」的平均，低于 0.7（同一维度的信号互相矛盾）时降一级。不足 30 个会话时 `hint` 提示「数据越多越准」但不扣留类型。

**任意 Agent 子集**：全部统计量都是可加的充分统计量——比率信号存 (Σk, Σn, m, Σk², Σkn, Σn²)，均值信号存 (Σs, Σs², m)，按天的信号存逐日 [会话数, Agent 数, 是否有重叠]。`/v1/uiview/persona` 先在时间窗与项目范围内按 Agent 各算一块（`persona_signals.by_agent`），再把所选 Agent 的块相加（`combine`）后计算维度，不为 2^n 个子集预计算或缓存。按 Agent 拆分的块互不重叠，逐日合并时会话数与 Agent 数相加、重叠取或（同一天出现两个 Agent 已经算多线），因此子集结果与直接在子集会话上计算完全一致（`tests/uiview/test_persona.py::test_any_agent_subset_equals_direct_computation`）。前端 live 行带每会话单位（`dk/dn/vk/ik/kn/ol/oa/os/sc/rb/t0/t1`），客户端按同一方式按 Agent 求块再相加（每个 Agent 的块按其会话切片缓存，切换侧栏只重新求和）。

同一会话的轮次相关，比率信号不能把轮次当独立样本。实现用比率估计的线性化方差 m/(m−1)·Σ(k_i − p·n_i)²/(Σn_i)²（Cochran 1977，*Sampling Techniques* §6.4）换算 Kish 有效样本量 n_eff = p(1−p)/var，上限为单位数；会话间方差为 0 时取会话数。再在 n_eff 处取 Wilson 区间。因此同一会话里重复的轮次不会缩窄区间。

### 画像页表盘：逐会话归类与 Agent 平均方向

表盘不是画像的另一套算法，只把同一口径落到单个会话上，用于「每个会话落在 16 型的哪一边」。它在前端（`prototypes/advance/src/js/41-a2-persona.js` 的 `fpSessV` / `fpClassify` / `fpOrbit`）完成，不改后端画像结果：

- **单会话四维**：与上表同一多信号口径，只看这一个会话和它所在的那一天：D / I / V 用该会话自己的信号，M 用当天的会话数、Agent 数与是否多线；示例数据用会话自带的四维倾向，仅供表盘归类，不参与其它统计。每轴限制在 4–96，以 50 为界取一极，得到该会话的类型码。
- **软归属与方位**：每个轴偏向高值一极的概率为 0.5 + (值 − 50)/50 × 0.45（限制在 0.05–0.95），四轴相乘得到 16 型上的分布；会话在自己的类型扇区里朝软归属更多的相邻一侧偏一点，得到连续方位（每型 22.5°）。点击、计数与徽章以最接近的类型为准。
- **每个 Agent 一条曲线**：该 Agent 的各会话方位各放一个 σ = 8° 的高斯核，得到密度；所有 Agent 共用一个高度尺度（全部 Agent、全部方位的最高密度对应最大起伏），所以曲线高低可以直接比较，曲线互相独立、不叠加。
- **Agent 徽章**：方位 = 该 Agent 全部会话方位的圆周平均（单位向量求和再取角），不吸附扇区、不找峰；与别的徽章或类型码相碰时沿轨道最小幅度错开，真实平均方向与所在类型留在提示里。
- 表盘与四轴人格共享同一套类型顺序（格雷码，相邻两型只差一个字母）；类型文案（名称与一句话）以 `05-data.js` 的 `TYPES` 与后端 `uiview/typecopy.py` 的 `type_copy` 为准，两处必须逐字一致。

### 阈值的来源与敏感性

所有门槛集中在 `uiview/persona.py` 的 `CONFIG`：

| 参数 | 值 | 依据 |
| --- | --- | --- |
| `soft_sessions` | 30 | 低于此会话数时给出样本量提示；正态近似常用的 n ≥ 30 经验下限，产品默认 |
| `consistency` | 0.7 | 信号一致性低于此值时置信度降一级；产品默认 |
| `midpoint` | 50 | 字母分界；产品决定始终给出完整类型 |
| `band` | 45–55 | 只用于 `decided` 标记：区间整体越过该带才算统计上已定型；产品默认，没有人群基线 |
| `step_threshold` | 5 | 来自 `uiview/facts.py`；产品默认，未校准：尚无真实的每轮步数分布，也未按 Agent 的工具粒度分档 |

`decided` 的敏感性：在有效样本量 n 下，要让 Wilson 下界越过高侧阈值，观测占比至少为

| 判定带 | n = 30 | n = 100 | n = 300 |
| --- | --- | --- | --- |
| 50–50（无带） | 67.9% | 59.9% | 55.7% |
| 45–55（默认） | 72.9% | 64.8% | 60.7% |
| 40–60 | 77.6% | 69.7% | 65.6% |

上表是单个占比信号的情况；v1 的维度区间由多个信号合成，敏感性随信号组合而变。合成数据（`tests/uiview/synth.py`）只能说明计算是否稳定，不能代表真实用户的分布。

事实层的判据（`uiview/facts.py`）：

- 验证命令按命令本身判断（`is_validation_command`）：去掉环境变量与 `uv run`、`npx`、`python -m` 等前缀后，命令头是测试/lint/类型检查工具（pytest、vitest、ruff、mypy、tsc 等），或构建工具的 test/check/lint/build 子命令（`cargo test`、`go vet`、`make check`、`pnpm run typecheck` 等）。`cd build`、`ls test/`、`git diff --check`、`docker build .` 不再算验证。Codex 的 `bash -lc "<脚本>"` 按脚本内容判断。
- 每个轮次记 `[步数, 验证, 用户要求, Agent 运行, 以中止状态结束, 状态已知]`。V 轴仍按「验证」（任一成立）计；画像证据分开列出「用户要求验证」与「仅 Agent 自行运行」的轮次数。
- 结构化开场只看列表（≥ 2 项）、验收词、规格/计划文档，以及指令层标出的 `execution_order` / `acceptance_criteria`；只提到文件名或消息很长（如粘贴报错）都不再算结构化。

局限：

- D 的步数 = 工具调用数 + 最终回复数，取决于 Agent 的工具粒度：Claude Code 每次 Read / Edit / Bash（含并行调用）各记一步；Codex 一次 `apply_patch` 可改多个文件（`third_party/codex/codex-rs/apply-patch`），一次 exec 也可以用 `&&` 串多条命令。同样的工作在 Claude Code 下更容易被判为「委托」。阈值 5 未校准，需在获得授权的真实数据上按 Agent 测出分布后再分档。
- V 轴目前仍把 Agent 自行运行的验证计入「求证」。Claude Code 等会默认自跑测试，因此只看「用户要求」更贴近用户自身的习惯，但会改变已有用户的字母，是否切换由团队决定。
- I 的结构、规格与长度只看首条消息，续会话会偏即兴；M 把同日顺序使用两个 Agent 也算作多线。
- 打断率只在 Agent 记录了轮次结束状态时可用（Claude Code、pi、hermes、opencode 等会写 interrupted）；没有状态的 Agent 该信号退出，不当成 0。子代理并行度只对记录子会话的连接器（Claude Code、Codex、Kimi、Hermes：`facts.SUBAGENT_AGENTS`）计入；其他 Agent 该信号为未知、退出并重新归一化，不当成「没有并行」。回滚的文字线索是词表候选，只看不超过 400 字的消息（跳过粘贴的日志与代码），仍可能误判。

## 在 CLI 中核对

```sh
.venv/bin/orbit demo --output .local/demo
.venv/bin/orbit --db .local/demo/demo.sqlite report --output .local/demo --view profile
.venv/bin/orbit --db .local/demo/demo.sqlite report --output .local/demo --view bottlenecks
.venv/bin/orbit --db .local/demo/demo.sqlite report --output .local/demo --view process
.venv/bin/orbit --db .local/demo/demo.sqlite evidence <报告中的证据ID>
```

同一目录下的 `profile.json / bottlenecks.json / process.json` 保存结构化副产品；对应 Markdown 便于阅读。`analysis.json` 保留完整结果，`report.md` 再解释推荐与下一步。技术模块见 [架构](../../architecture/backend.md)，统计假设见 [建模说明](modeling.md)。
