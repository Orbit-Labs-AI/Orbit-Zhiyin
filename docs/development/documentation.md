# 文档维护

Orbit 文档按读者任务与证据状态组织。根 README 帮新读者理解产品并开始使用；详细规则各维护一份正文，其他入口链接过去。

## 目录职责

| 目录 | 应放的内容 |
| --- | --- |
| `getting-started/` | 安装、第一步、无需个人数据的示例 |
| `guides/` | 用户完成具体任务的步骤与排障 |
| `product/` | 当前交付范围与产品概念 |
| `architecture/` | 模块依赖、进程和数据所有权 |
| `contracts/` | 已实现接口的字段语义、范围与兼容规则 |
| `development/` | 开发环境、检查、构建、维护与验收方法 |
| `modules/` | 各模块的当前算法、入口和边界 |
| `design/` | 当前视觉规范、源素材与展示资产 |
| `plans/` | 尚待确认的方向和决策问题 |
| `audits/` | 绑定版本、数据与环境的检查结果 |
| `releases/` | 版本交付记录的导航 |
| `archive/` | 已替代的方案、设计演变、迁移与事故记录 |

每个分区的 README 维护该区入口，`docs/README.md` 只维护读者路线。研究（竞品与选型、外部源码和日志格式、轨迹建模与文献）不放在本仓库，在 TeamHub 的 [Orbit 项目页](https://github.com/Orbit-Labs-AI/team-hub/blob/main/%E9%A1%B9%E7%9B%AE/Orbit/README.md#%E7%A0%94%E7%A9%B6) 维护，这里只链接；同一篇正文只在一边维护。不要恢复 `docs/plan`、`docs/backend` 或 `docs/design/demo`，不要在文档目录建立新的运行入口。

## 写当前手册

先说明谁在什么情况下使用本页，再给步骤、可观察结果和边界。命令从仓库根执行，并明确前置环境与数据目录。真实来源示例必须显式选择来源；示例数据与真实数据分开。

说明功能时区分代码已实现、UI 已接入、下载版本已发布和效果已验证。不要用测试条数证明算法有效，不把构造耗时写成 SLA，不把未知值写成零。API 与数据库以实现和机器 Schema 为权威，手册解释语义而非复制第二套 Schema。

包内 README 说明该包如何接入和验证；根贡献指南解释社区流程；`AGENTS.md` 维护自动化协作约束。不要在用户指南复制内部任务清单或 agent 操作指令。

## 保留历史

计划和审计不能随新实现改写成“当时已完成”。旧正文需要保留时移入 archive/audits，注明状态、原基线和现行入口。历史版本号、实测数字与引用只对原文上下文成立；没有重新执行，就不更新“已验证”时间。

本轮重组将旧 `plans/*.md` 与功能映射 CSV 归入 `archive/plans/`，将模块内测试报告归入 `audits/`，将迁移、设计演变与导入事故归档。版本记录保留证据，不作为当前能力清单。

## 搬迁与验证

移动文件时同时修正入站链接和文件内部的相对链接，检查锚点、图片与代码中的文档路径。新增页面在所属 README 登记，必要时补主导航。保持已有品牌素材路径和生成机制。

运行 `pnpm check:docs` 与 `git diff --check`。命令/API 示例另按实际入口核对；纯文档无需扩展成全量测试。返回[开发手册](README.md)。
