# 分析模块规范与功能补全建议

给 `yhyfhgs`、`MistyHuang03`、`genius-FXC` 的讨论稿，2026-10-02。核对基线为 main `f834616` 与合入后的开发分支 `d95b84f`；分析代码以主干为准，Advance 同时参考本地开发中的设计。这里只讨论分析，不讨论推荐、资源匹配与安装。

**建议保留八个族，先统一计算与证据口径，再补跨族组合功能。** 八族已经覆盖“做什么、有什么要求、偏好什么、如何互动、怎样执行、花费多少、验证如何、用户是否接受”的主链；尚不能覆盖两版 UI 的全部交互。下文是工程与产品建议，不代表新增 MVP 承诺，范围仍需三位成员共同确认。

## 后端怎样变得规范

当前已有统一数据库适配、`AnalysisInputBundle`、`Scope`、字段字典、八族实现和回归测试，基础应保留。主要问题是编排过重、族间接口不齐、分析口径在新旧入口重复，以及 UI 仍使用演示公式。

| 当前事实 | 建议调整 |
| --- | --- |
| `analytics/service.py` 的 `analyze_bundle` 有 176 行，混合任务提取、会话分析、项目汇总和响应拼装。 | 按“选择数据、建立索引、运行各族、汇总范围、组装响应”拆成有名称的步骤，入口只展示计算顺序。 |
| 会话、项目、全局分别调用分析，同一范围还重复计算 `workflow`、`usage` 和工具汇总。 | 共用一次按会话建立的索引和中间结果，计数可相加，比率、分位数、区间并集和去重任务按各自口径重新汇总。 |
| 四个执行相关族有 `analyzer.py`，其他族使用 `features.py`、`extraction.py` 或 `__init__.py` 作为入口。 | 为每族提供一个稳定公共入口，内部按需要拆文件，不要求小模块也凑齐固定目录模板。 |
| 大量边界使用无类型字典，字段遗漏主要靠运行时与测试发现。 | 先为共享输入、证据引用、指标结果和各族公共返回加类型，沿用 dataclass、TypedDict 与已有 Pydantic。 |
| `analysis.py`、`portrait.py` 的报告链与 `analytics/` 特征链并存。 | 逐步让旧报告消费同一份分析结果，兼容入口只负责字段转换，避免两套画像和纠偏算法各自变化。 |
| `resolve_instruction_scope` 已实现，但统一服务只输出提取记录与摘要。 | 将“任务当时有效的要求”接入任务详情，再用于核对后续执行与验收。 |
| Instruction 输出验收要求候选，Outcome 读取 `attrs.acceptance` 中已确认的结构化标准。 | 补上候选确认与标准关联流程，保留任务、产物版本和证据；词面命中不能直接升级成验收事实。 |
| API 各页面请求会再次调用完整分析引擎。 | 先支持按页面选取所需分析，再根据实际耗时决定是否缓存；缓存需包含数据版本、全部规则版本与完整筛选条件。 |
| 字段已有多种版本标识，但总分析摘要没有显式包含所有族的规则版本。 | 每次分析记录所有参与族的版本，使同一数据的结果变化能追到具体规则。 |

建议的职责顺序是：**读取统一数据 → 统一筛选 → 八族分析 → 画像／瓶颈／轨迹／趋势组合 → API 与报告展示**。组合层只消费各族结果，不再另读日志或另建词表；现有兼容字段逐步迁移，不为整理目录一次性改名。

所有分析遵守五条共同口径：

1. 数字说明统计的是消息、轮次、调用、任务还是会话；用户消息数不能冒充轮数。
2. `0` 表示有覆盖且没有发生，`null` 表示无法判断，同时保留数据不足、部分覆盖和主动排除的原因。
3. “日志事实、规则候选、人工确认、模型推断”分别标注；规则可复现不等于语义判断已被确认。
4. 比例带有效分母，结论能回到原始证据；需要阈值的判断先约定单位与校准方式，不给所有指标统一套“至少 30 个会话”。
5. 时间窗口统一使用半开区间，窗口外历史只作必要上下文，未来反馈不改变过去快照。

## 函数怎样易读且可维护

静态核对 `analytics/` 的 Python 函数，排除推荐子目录：共 94 个函数，其中 34 个有 docstring，只有 1 个同时标注了全部普通参数与返回类型。这个计数只说明文档与类型覆盖，不代表其余函数都需要重写。

| 约定 | 具体做法 |
| --- | --- |
| 名称直接说明动作 | 使用 `extract_validation_runs`、`summarize_interactions` 一类名称，业务循环里用 `session`、`call`、`events_by_session` 替代多层含义的单字母。 |
| 一个函数处理一个阶段 | 遇到“提取后顺便汇总、又修改历史、最后拼 API”就按阶段拆分，不按行数机械拆函数。 |
| 公共函数有明确类型 | 标清输入实体、时间单位、可选值和返回结构，调用处不必猜字典里有什么。 |
| 业务函数有一句话说明 | 第一句写“做什么”，只有缺失值、分母、时间边界或副作用容易误读时再补一句。 |
| 注释说明原因 | 保留“包装层成功不能证明内部成功”“未来反馈不能进入历史快照”等注释，删除只复述赋值与循环的注释。 |
| 规则与计算分开 | 词表、阈值和枚举放在所属族中集中维护，提取、关联和汇总函数各自清楚。 |
| 不暗改输入 | 接收的数据按只读处理，使用显式返回值传递任务映射等中间结果，减少 `pop` 和共享字典修改。 |
| 少量关键例子比长注释有效 | 每条规则保留正常例、反例及真正相关的边界例，重点覆盖缺失、冲突、重复与历史截止时间。 |

例如，“统计工具失败率；只将明确成功和失败计入分母，无法计算时返回未知”已经能说明一个函数的核心行为，无须在函数前复制整份字段字典。

落地顺序建议为：先整理 `analyze_bundle` 与公共类型，再完善各族入口和一句话注释，最后迁移重复的旧报告计算；功能变更与纯整理分开提交。现有检查仍照项目约定执行，逐步加入公共接口类型检查即可，无须新增框架或大批只验证实现细节的测试。

## 八族与二维分类是否合理

**八族作为业务职责划分相对完整，2×2 作为查看角度合理，但不适合把每个族强行放入唯一格子。** “画像／瓶颈”描述用途，“语义／结构化事实”描述分析依据；两条轴可以交叉，同一指标也能服务多个用途。

建议将 `semantic / objective` 的展示名称改为“内容理解／结构化事实”。“用户说满意”是一条客观记录，但内容属于主观反馈；用 `objective` 表示“不读语义”容易混淆。模型提取、关键词规则和人工标注是另外的证据来源标签，不另设业务族。

| 用途 | 结构化事实 | 内容理解 |
| --- | --- | --- |
| Portrait 画像 | Interaction 的介入节奏、Respond 的工具习惯、Cost-Time 的活动与用量分布。 | Task 的任务主题、Preference 的明确偏好、Instruction 的要求习惯，以及 Subjective Outcome 的反馈表达。 |
| Bottleneck 瓶颈 | Respond 的失败与重试、Cost-Time 的耗时与资源集中、Outcome 的未通过验收。 | Interaction 的纠偏原因、Instruction 的要求与执行偏差，以及 Subjective Outcome 的拒绝与返工反馈。 |

这张表是建议的归类方式：已有实现提供其中的部分事实，要求偏差、完整画像等仍待补。一个族可跨格复用，具体特征只保留一个实现归属。

八族边界可简化为：

| 族 | 一句话职责 |
| --- | --- |
| Task 任务 | 说明用户这次要完成什么，以及哪些消息和执行属于同一个任务。 |
| Instruction 当次要求 | 记录这次任务要求怎样做、不能做什么、怎样才算完成。 |
| Preference 持续偏好 | 记录用户明确表达的长期习惯，以及它适用于哪里、何时改变。 |
| Interaction 人机互动 | 描述用户何时介入、是在澄清还是纠偏，以及哪里反复沟通。 |
| Respond 响应与执行 | 描述 Agent 实际调用了什么、执行顺序如何、失败和重试发生在哪里。 |
| Cost-Time 用量与时间 | 说明用量和时间花在何处，并区分可靠测量、估算与未知。 |
| Outcome 客观验收 | 判断当前产物是否通过明确的验收要求，并指出缺少哪项验证。 |
| Subjective Outcome 用户反馈 | 记录用户对哪次交付表示接受、拒绝或要求返工。 |

无需为画像、趋势、轨迹、实时状态再增加四个业务族：它们是跨族结果的组合；配置清单、数据覆盖和证据定位则是共享能力。只有出现无法归入这八种职责的新问题时，再讨论新增族。

## 按族列出的功能缺口

“已有”指当前源码已有实现，不等于真实日志覆盖充分或已通过团队验收；“补齐”指已有基础但未形成所需功能，“新增”指当前分析链未见对应完整实现。下列都是候选范围，**优先**表示建议先做，不代表已排入 MVP。两版指 Lite 与 Advance。

### Task 任务

已有：识别候选任务边界、目标及目标变更、领域、任务类型、预期产物和可信跨会话关联，并提供文本聚类与坐标。

| 功能 | 一句话说明 | 状态与页面 |
| --- | --- | --- |
| 任务与执行关联 | 将工具调用、助手交付和子代理挂到对应任务，无法确认的关联单列未知。 | 补齐／优先；两版会话轨迹 |
| 任务阶段 | 将同一任务中的调研、规划、执行、验证和收尾串成阶段，避免把每次阶段切换都显示成新任务。 | 补齐；两版任务节点、Advance 阶段带 |
| 可解释的主题 | 为会话簇提供有出处的主题词或候选标题，并支持查看该主题的会话。 | 补齐；两版语义兴趣 |
| 任务分布变化 | 比较不同时段与项目中任务类型的变化，并显示未分类任务数量。 | 新增；两版画像、项目分析 |
| 任务边界修正 | 允许用户确认或修正候选任务的拆分与合并，并据此重算关联统计。 | 新增；后续完善，不是现有 Demo 的直接承诺 |

### Instruction 当次要求

已有：提取自主程度、执行顺序、验证要求、允许范围、禁止动作、验收条件、格式和工具要求，并实现按任务与时点解析有效要求的函数。

| 功能 | 一句话说明 | 状态与页面 |
| --- | --- | --- |
| 当时有效的要求 | 在任务详情显示执行当时应遵守的要求，以及后续补充或撤销发生的位置。 | 补齐／优先；两版会话详情 |
| 可核验的验收清单 | 将明确且已确认的验收要求关联到相应验证项，让 Outcome 能逐项核对。 | 补齐／优先；两版任务结果 |
| 要求与执行偏差 | 对有明确对应证据的情况指出越界、漏验证或顺序不符，其余保持待确认。 | 新增；两版摩擦、Advance 关键时刻 |
| 规划与求证习惯 | 统计任务开始前明确提出计划、边界和验证要求的情况，为协作画像提供证据。 | 补齐；两版四维画像 |

### Preference 持续偏好

已有：识别语言、详略、格式、工具和协作方式偏好，保留适用范围、修改、撤销、重申与冲突，并可查询当前筛选内的有效偏好。

| 功能 | 一句话说明 | 状态与页面 |
| --- | --- | --- |
| 窗口之前仍有效的偏好 | 查看本月任务时带入此前仍有效的偏好作为背景，同时不把旧消息重复计入本月。 | 补齐／优先；两版画像与任务解释 |
| 偏好的稳定与变化 | 区分反复明确表达的习惯、仅出现一次的要求和近期改变，列出支持它们的不同任务。 | 新增；两版画像演变 |
| 项目偏好差异 | 展示同一用户在不同项目中的明确偏好差异，避免把项目习惯当成全局人格。 | 补齐；两版项目画像 |
| 偏好确认与纠错 | 允许用户处理“这不是我的偏好”和相互冲突的表达，并保留修改记录。 | 新增；Advance“不是我／不像我”反馈的基础 |

### Interaction 人机互动

已有：消费已确认的消息意图和摩擦标签、定位介入位置、统计确认纠偏及重复要求，同时把关键词候选单列。

| 功能 | 一句话说明 | 状态与页面 |
| --- | --- | --- |
| 纠偏证据链 | 将每次确认纠偏连到被纠正的步骤及后续处理，未确认的词面命中保持候选。 | 补齐／优先；两版摩擦与轨迹 |
| 每轮介入节奏 | 统计用户两次介入之间 Agent 连续执行的步骤，并区分补充要求、澄清与纠偏。 | 补齐；两版委托／掌舵维度 |
| 反复沟通片段 | 找出同一任务中针对同一要求反复澄清或纠偏的片段，保留每次发生的位置。 | 补齐；两版关键任务、Advance 关键时刻 |
| 高频反馈语 | 从真实真人消息提取重复短语，并让每个短语都能打开实际出现过的消息。 | 新增；两版反馈语、Advance 出处下钻 |
| 审批负担 | 统计明确的审批请求、拒绝和重复确认，仅在请求与处理端点齐全时计算等待时间。 | 补齐；Advance 工具页与等待提醒 |

### Respond 响应与执行

已有：调用配对与去重、工具状态和失败原因、重试关系、状态转移、子代理与分叉关系，以及可靠执行和并行区间。

| 功能 | 一句话说明 | 状态与页面 |
| --- | --- | --- |
| 工具之间的转移 | 按相邻工具名称或类别计算“下一步通常调用什么”，并能展开每条转移对应的调用。 | 补齐／优先；两版工具矩阵，已有的是事件状态转移 |
| 失败后的恢复 | 将明确失败、关联重试和最终结果串起来，区分已恢复、仍失败和结果未知。 | 补齐／优先；两版失败明细与轨迹 |
| 常见执行流程 | 找出同一项目中反复出现的真实步骤组合，并列出支持该流程的会话。 | 新增；Advance 项目工作流 |
| 运行状态汇总 | 从新增事件更新运行中、等待确认、已结束和状态未知，并保留最新事件时间。 | 新增；Advance 菜单栏、悬浮组件 |
| 实际文件与语言使用 | 根据有记录的文件操作统计涉及的语言，和仅在提示语中提到的文件扩展名分开展示。 | 补齐且需数据支持；Lite 语言排行 |

### Cost-Time 用量与时间

已有：Token 分桶与累计快照处理、已有费用记录汇总、请求延迟、首 Token 延迟、执行时长、可靠区间并集和日／小时活动统计。

| 功能 | 一句话说明 | 状态与页面 |
| --- | --- | --- |
| 真实用量卡 | 汇总当前范围内可确认的 Token 与费用，同时列出缺失记录和估算来源。 | 补齐接入／优先；Lite 用量卡、Advance 用量视图 |
| 时间分解 | 分别展示可靠执行时间、可确认等待、日志跨度和无法归类的时间，避免把跨度称为工作时长。 | 补齐；两版时长、Advance 时间线 |
| 重试开销 | 汇总已关联重试的调用次数、耗时和可归属用量，指出资源集中在哪些失败链。 | 新增；两版工具与会话分析 |
| 分组趋势与上期对比 | 按项目、模型与思考档位比较相同口径的用量和时间变化，并保留不可比项。 | 新增；两版概览与项目分析 |
| 多任务交错 | 用可靠活动片段区分并行执行与任务切换，为多线／专注画像提供依据。 | 新增；两版画像，不能用 Agent 数代替 |
| 上下文与额度状态 | 仅在来源提供真实占用、容量或额度窗口时显示状态及临近上限提醒。 | 新增且需数据支持；Advance 运行面板 |

### Outcome 客观验收

已有：识别验证运行、匹配显式验收项与产物范围、处理验证结果新旧关系，并只在验收集合完整时判断该集合是否通过。

| 功能 | 一句话说明 | 状态与页面 |
| --- | --- | --- |
| 验收状态卡 | 分别展示已要求、已运行、已通过、未通过和证据不足的验证项，并指向对应结果。 | 补齐／优先；两版会话结果 |
| 修改后的验证有效性 | 在产物再次修改后指出旧验证是否仍覆盖当前版本，版本缺失时保持未知。 | 补齐且需版本证据；两版会话详情 |
| 首次通过与返验 | 统计同一明确验收项从首次检查到通过经历了几次验证与失败。 | 新增；两版效率分析 |
| 项目验收分布 | 展示项目中各任务的通过、未通过和未知数量，不将其命名为真实项目进度。 | 补齐；Lite 完成度散点、Advance 项目分析 |

### Subjective Outcome 用户反馈

已有：提取明确反馈、关联交付对象、区分接受／拒绝／混合反馈与返工要求，并保留每次交付的反馈变化；沉默保持未知。

| 功能 | 一句话说明 | 状态与页面 |
| --- | --- | --- |
| 交付反馈卡 | 在会话详情同时展示用户接受情况与客观验收情况，避免把两者合成一个成功结论。 | 补齐／优先；两版会话与项目结果 |
| 返工与再次接受 | 串起同一产物的交付、返工要求、后续版本和再次反馈，显示哪些返工已有明确收尾。 | 补齐；两版任务结果与轨迹 |
| 不满意的具体对象 | 区分反馈针对内容、格式、范围还是执行过程，并展示用户的实际原话。 | 新增；两版反馈与摩擦分类 |
| 表达情绪的变化 | 按时段汇总有证据的情绪表达并允许纠正，不能直接把纠偏次数当成负面情绪。 | 新增、实验性；Advance 情绪曲线 |
| 反馈与执行的关联 | 比较不同执行特征下的反馈差异并显示样本量，避免把相关关系写成情绪成因。 | 新增、实验性；Advance“情绪的前因” |

## 八族之外还需要的共享能力

这些能力组织已有分析，不新增业务族，也不涉及推荐。

| 能力 | 一句话说明 | 当前基础与缺口 |
| --- | --- | --- |
| 一致的筛选与下钻 | 点击某个指标或图形后打开真正参与该统计的会话、任务与消息。 | 已有项目、时间、模型等筛选和证据接口，需补来源筛选及主题、摩擦、工具等成员定位。 |
| 会话检索与排序 | 按标题或项目查找会话，并按最后活跃时间稳定排序、分页。 | 已有会话分页接口，需补与两版列表一致的查询能力。 |
| 统一轨迹与关键时刻 | 将任务阶段、用户介入、调用、失败和验收组织成可定位的时间与步骤序列。 | 已有事件接口和各族证据，缺 Lite 简化节点与 Advance 回放可共用的轨迹结果。 |
| 一致的会话对比 | 用相同定义并排显示两个会话的任务、步骤、用量、时间和结果。 | 可读取两份会话详情，Advance 还需统一时间／步数对齐规则。 |
| 有依据的四维画像 | 分别展示委托方式、规划习惯、任务交错和求证行为，并让每个倾向都能回看证据。 | 旧 `portrait.py` 只有要求与交互描述，尚无可替换 Demo 公式的完整四维模型。 |
| 可回看的画像历史 | 按每个月当时可见的数据重算画像，让 Lite 完整历史与当前范围的差异清楚可见。 | 有历史可见性规则，缺按月画像产品与统一端点。 |
| 数据可用性说明 | 在图表与数字旁说明数据覆盖、更新时间、估算依据及无法计算的原因。 | 已有 coverage、版本和未知计数，需统一为两版可直接展示的状态。 |
| 配置覆盖快照 | 显示已授权读取的项目配置与观测时间，区分“已配置”“日志中用过”和“未扫描”。 | 当前分析未接入配置清单，需数据层提供；不能从没调用推断没安装。 |
| 排除与人工纠错 | 保存用户的会话排除和标签修正，使所有页面同步重算并支持恢复。 | 已有查询时排除参数，缺完整的持久化设置与标注写入流程。 |
| 报告与页面同源 | 用同一份筛选结果生成报告、CSV 和分享统计，避免导出的数字与页面不同。 | 已有旧报告导出，需接入统一分析结果与对应数据版本。 |

两版共用核心分析服务；Advance 的回放、对比、实时提醒和实验性情绪关联按需启用。Lite 不需要为了共用后端而获得这些额外页面或操作。

## 应优先修正的演示口径

| 演示中的做法 | 接真实数据时的处理 |
| --- | --- |
| 两版 `stats / persona` 使用工具数 × 1.54、手填项目参数等公式。 | 用真实轮次、要求、任务交错和验证证据替换，四维定义与阈值未确认前显示行为事实。 |
| Lite 用消息数显示对话轮数，用会话跨度累计协作时长。 | 轮次来自明确轮次记录；跨度与执行时长分别命名。 |
| Lite 工具成功率用“总调用减错误”推算。 | 只在已知成功与失败中计算成功率，拒绝、中断、运行中和未知另列。 |
| Lite 完成度给部分完成固定计 0.5，Advance 也依赖示例结果字段。 | 改为展示验收和用户反馈的状态分布，产品若保留综合分需另行定义并确认。 |
| 工具矩阵、失败原因、工作流支持度、部分短语及其出处来自样例或比例缩放。 | 接入实际成员与证据，没有数据时显示未知或空状态。 |
| Lite 的画像散点是模拟的委托／求证轴，后端已有坐标是文本相似度。 | 分开使用两种坐标；文本聚类点不能直接贴上人格坐标轴。 |
| Advance 原设计含全体用户比较、Agent 契合度和情绪成因式文案。 | 遵循设计 README 的后续决定，去掉无数据来源的全体用户比较，以可核实行为替代未经验证的评分。 |

建议先做统一筛选与证据下钻、任务执行关联、有效要求与验收链、真实统计接线；其次做阶段轨迹、趋势和可解释画像；最后再考虑实时上下文提醒、复杂语义和情绪关联。不能仅为填满 Demo 而生成没有依据的数字。
