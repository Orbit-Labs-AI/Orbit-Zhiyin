# v0.2：推荐开始由分析结果决定

> 状态：历史版本记录；描述当时行为，当前入口见仓库 README。
这版补上了第一版缺少的关系：先从历史中提取协作要求，再找相关结果或修改记录，最后匹配能处理这个问题的资源。只发现“希望写得简洁”时，不再直接推荐写作 skill。

## 现在能看到什么

合成 demo 包含两条完整链路。解释任务要求易懂，但回答开头堆了术语，系统给出写作资源的试用建议；开发任务要求跑通和检查，同一命令连续失败三次，系统给出先定位原因的调试建议。两条建议都能回看要求与结果。移除画像、瓶颈或场景匹配，建议就会消失。

真实样本中，系统观察到若干说明修改要求，推荐先试文档的读者测试流程。它没有把这些修改一律判为失败。部分交付记录只含文件链接，没有正文，因此仍无法核对实际文档质量。

## 为什么改这些

“代码简洁”“图表坐标太长”“说明简短”指向不同对象，不能混成写作偏好。这版先判断要求的对象，过滤了已发现的代码、排版和题量误判。英文任务也按其输出语言匹配资源。

Codex review 指出了两处值得修复的问题，均已采纳：收紧导入范围时，清除之前已保存但现在被排除的会话；按具体语句识别纠正，避免“很好，但还是太长”被误判为接受。SQLite 连接也在使用后关闭。

## 验证与下一步

16 项后端测试、lint、合成 demo 和场景检查通过，真实历史快照重新导入并生成了报告。新增检查覆盖推荐的双重依据、错误对象过滤、历史隔离策略变更与一句话中的不同反馈。

目前仍是保守的规则基线。连续失败未必是浪费，修改要求未必是拒绝，推荐收益仍未测过。下一版先把资源获取变成可复现的采集步骤，并扩大独立评价样本；同时继续复核真实记录中的误判。
