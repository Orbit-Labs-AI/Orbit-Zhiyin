# benchmark硬效果

> 历史来源：本页为2026-10-01 至 10-03 的历史方案，2026-10-07 从团队 Vault 迁入。原位置：`项目/Orbit/benchmark/benchmark硬效果.md`。正文与原有日期、结论保留，仅整理导航和空白；私人会话定位不公开。本文中的“当前”、TODO、测试数量和执行命令仅对原文基线成立，本次没有重新验证，也不自动形成任务或授权。现行入口：[源码文档](<../../../../evals/README.md>)。

**黑客松只做一套配对实验：12 个小任务 × 2 组，共 24 次执行，同时拿到 Token、时间、完成率、纠错四个数字。** 用它回答“Orbit 到底有没有让 Agent 做得更好”。

按本轮要求缩减范围。下面是执行提案，尚未实测；样本数和预算是计划，不是结果。具体取舍仍由团队确认，不扩产品功能。

## 两组怎么比

| 组别 | 做法 |
| --- | --- |
| A：平常怎么用 | 现有 Agent，保留本来就有的 memory、rules、工具与配置 |
| B：加上 Orbit | 与 A 完全相同，再应用 Orbit 根据此前历史给出的具体建议 / Skill / 规则 |

同一任务用相同起始文件、输入、模型、推理档位和验收检查；每组独立恢复环境。建议在测试前固定，不能看完失败再为 B 定制答案。每任务使用固定的 10k 总 Token 执行预算、5 分钟、最多 2 轮纠错反馈；Orbit 的一次性分析成本另外实记，并扣入净节省。

## 只看四类硬效果

| 要回答的质疑 | 主指标 | 展示方式 |
| --- | --- | --- |
| “分析历史本身就很贵，真的省 Token 吗？” | 双方都成功的任务上，扣除 Orbit 分析 / 推荐开销后的净 Token 节省 | A / B 总量、净减少量、净减少百分比、成功配对数 |
| “步骤变复杂了，会不会反而更慢？” | 同一成功配对子集的净用时变化 | 每任务耗时配对图；总计少 / 多多少分钟，准备开销单列 |
| “省资源只是因为少做事吧？” | 全部任务在共同执行预算内的完成率；首次交付通过率 | 各自成功数 / 12，变化用百分点；失败任务全部保留 |
| “真的更懂我，还是还要我一直纠正？” | 需要纠错的任务数 / 12；每任务平均纠错回合 | 从多少个任务降到多少个、少了多少次纠错，附对应证据 |

完成度可补充“预先列出的验收项通过比例”，但不能把部分完成算成功。用户纠错、工具报错和 Agent 自行重试分开计数。定义和计算方式见[共同协议](<paired-protocol.md>)。

## 12 个任务怎么选

| 分类 | 数量 | 选择方向 | 主要展示 |
| --- | --- | --- | --- |
| 修错与验证 | 4 | 小型 bug、已有失败测试、清晰可验收的修复 | 完成率、首次通过率、重复失败与 Token |
| 实现与交付 | 4 | 小功能、补测试、有限范围重构；验收清单固定 | 完成率、Token、用时 |
| 约束与协作 | 4 | 已有历史偏好的格式、命令、修改范围、先说明后修改等 | 纠错任务占比、纠错回合、返工用时 |

优先选能保存当前 checkpoint 的新任务或尚未执行的留出任务，不花时间考古恢复旧工作区。先固定全部任务再开始跑，不能挑表现最好的 12 个。约束组也必须有真实工作产物和验收，不能只问 Agent“你记住了吗”。已有需求两组都能看到，A 不被故意拿走工具或规则。

样本来自真实需求就写“真实任务”；人为构造则写“受控场景”。Orbit 没有实际生成某项干预时，可以单列手工建议验证其潜力，但不能归为 Orbit 自动推荐效果。

## 有余力只加一个对照

测试开始前，每类选定 2 个任务，共 6 个，加 C 组“固定通用建议 / Skill”，其余条件不变；总量从 24 增至 **30 次执行**。

它回答“是不是随便加个 Skill 都一样”。B/C 只在这 6 个匹配任务上比较。若 B 没优于 C，就说明暂时只证明了干预有用，个性化选择的增益还未证明。时间不足跳过 C，并收窄结论，不做完整 action sweep 或 oracle。

## 排期与台上呈现

先用 2 个不进正式结果的构造小例子检查记录链路，再固定正式任务。24 次执行的 Token 上界为 24 万，另加一次性分析；试跑最多再 4 次、4 万 Token。单机正式执行的 5 分钟预算合计至多 120 分钟，准备、排队和汇总另留时间。时间更紧就事先定为每类 2 个，共 6 任务 / 12 次执行，不能跑完再删样本。

分成 3 个 session：准备与汇总、修错 / 实现执行、约束 / 纠错执行；复制[并行 Session 执行说明](<paired-session-prompts.md>)即可。各 session 按任务分工，一次执行记录全部指标，不为每个指标重跑。

最终只需要一页：顶部四个数字，中间一张逐任务 A/B 表，下面一个有日志可回看的案例。数字暂用“待测”，不要预填理想提升；同时保留失败数、成功配对数、分析成本和运行条件。小样本是黑客松试验结果，不写成普遍效果或统计显著。

本轮不排跨用户、滚动窗口、全特征精度、检索榜单、长期效果和系统吞吐。原 60 项完整方案保留在[后续扩展](<expanded/README.md>)，不再作为本轮任务清单；已有必要回归检查照常执行。
