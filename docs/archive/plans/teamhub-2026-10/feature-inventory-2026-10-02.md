# 分析Feature一览

> 本页是 2026-10-01 至 10-03 的历史方案，内容待团队确认；文中的“当前”、TODO、测试数量和命令只对当时成立。现行入口：[文档导航](<../../../README.md>)。

这里的 feature，就是**能从历史记录中数出来、算出来，或找到明确线索的东西**。

按特征族补充定义、分析函数和跟进开发进度，请进入 [分析模块分类与 Feature TODO](<analytics/classification.md>)。

这份清单对应当前 Feature Analytics MVP，覆盖正式特征字典的 **77 个字段**，并补上结果中另外返回的流程、聚类、项目汇总和数据质量信息；同一个指标在多个接口出现时合并说明。

**已可算**表示能在已有记录中计算，**部分**表示只能覆盖部分记录或只能作为线索，**待数据**表示当前历史缺少必要信息；未知不是 0，没看到也不代表没发生。

以下内容依据现有代码核对整理，文字表述待 `MistyHuang03` 确认。

## 二、什么时间在使用

日期和小时都按分析时指定的显示时区统计，没有时间的记录不会硬塞进某一天。

| Feature | 字段 | 一句话说明 | 当前情况 |
| --- | --- | --- | --- |
| 每天开始的会话数 | `sessions_by_day` | 每一天有多少个确认的主会话开始留下记录。 | 已可算 |
| 各小时开始的会话数 | `sessions_by_hour` | 一天的 24 个小时中，各有多少个确认的主会话开始留下记录。 | 已可算 |
| 每天的真人消息数 | `human_messages_by_day` | 每一天能确认是人发出的消息有多少条。 | 部分 |
| 各小时的真人消息数 | `human_messages_by_hour` | 一天的 24 个小时中，各有多少条确认的真人消息。 | 部分 |
| 每天的工具调用数 | `tool_calls_by_day` | 每一天记录了多少次工具调用。 | 已可算 |
| 每天的模型请求数 | `model_usage_by_day` | 每一天向模型发出了多少次可确认的请求，而不是把累计 token 平摊到每天。 | 待数据 |
| 活跃天数 | `active_days` | 在选定范围内，有多少个不同日期出现过确认的真人消息。 | 部分 |
| 星期分布 | `weekday_distribution` | 确认的真人消息分别有多少出现在周一到周日。 | 部分 |
| 小时分布 | `hour_distribution` | 确认的真人消息分别有多少出现在一天的各个小时。 | 部分 |

这些是特征字典中的名称，实际 JSON 将时间统计放在 `activity_rhythm` 下；每类记录还各自返回按天、按小时、按星期的分布和活跃天数，其中工具活动不能直接当成人的作息。

## 三、工具用了多少、结果怎样

“工具成功”只描述该次调用的协议结果，不表示整个任务成功；这里数的是日志中明确出现的调用，包装脚本内部未展开的操作不会被凭空补上。

| Feature      | 字段                               | 一句话说明                                | 当前情况          |
| ------------ | -------------------------------- | ------------------------------------ | ------------- |
| 工具调用次数       | `call_count` / `tool_call_count` | 一共调用了多少次工具，同一次调用和它的返回只算一次。           | 已可算           |
| 有返回的调用数      | `paired_result_count`            | 有多少次工具调用能找到与它对应的返回记录。                | 已可算           |
| 未配对调用数       | `unpaired_count`                 | 有多少次调用暂时找不到对应的返回，原因可能是尚未结束或记录缺失。     | 已可算           |
| 明确成功次数       | `known_success_count`            | 有多少次调用通过明确的返回信息确认成功。                 | 部分            |
| 明确失败次数       | `known_failure_count`            | 有多少次调用通过明确的返回信息确认失败。                 | 部分            |
| 明确被拒绝次数      | `rejected_count`                 | 有多少次调用被明确标记为拒绝，未识别出的拒绝仍留在未知状态里。      | 部分            |
| 明确被中断次数      | `interrupted_count`              | 有多少次工具调用被明确标记为中断。                    | 部分            |
| 明确仍在运行次数     | `running_count`                  | 有多少次工具调用被明确标记为仍在运行。                  | 部分            |
| 状态未知次数       | `unknown_status_count`           | 有多少次调用还不能可靠判断是成功、失败、拒绝、中断还是运行中。      | 已可算           |
| 已知状态中的成功率    | `success_rate`                   | 在明确成功或失败的调用中，成功调用占多少比例。              | 部分            |
| 已知状态中的失败率    | `failure_rate`                   | 在明确成功或失败的调用中，失败调用占多少比例。              | 部分            |
| 耗时中位数        | `median_duration_ms`             | 把可用耗时排好后，约一半调用的耗时不超过这个数。             | 部分：当前为日志时间差估算 |
| 耗时下四分位数      | `p25_duration_ms`                | 把可用耗时排好后，约四分之一调用的耗时不超过这个数。           | 部分：当前为估算      |
| 耗时上四分位数      | `p75_duration_ms`                | 把可用耗时排好后，约四分之三调用的耗时不超过这个数。           | 部分：当前为估算      |
| 耗时 P90       | `p90_duration_ms`                | 把可用耗时排好后，约九成调用的耗时不超过这个数。             | 部分：当前为估算      |
| 调用耗时总和       | `duration_sum_ms`                | 把有记录的调用耗时相加，其中并行执行的重叠时间会被重复相加。       | 部分：当前为估算      |
| 不重复计算的运行覆盖时间 | `reliable_interval_union_ms`     | 只用可靠的开始和结束时间合并区间，让同时运行的工具不会把同一秒重复计算。 | 待数据           |

### 反馈、模型与聚类的补充

| Feature／辅助信息 | 字段 | 一句话说明 | 当前情况 |
| --- | --- | --- | --- |
| 具体纠偏线索 | `correction_signals` / `correction_terms` | 列出哪些消息命中了哪些调整用语，以及这些用语出现了多少次。 | 部分 |
| 明确工具失败记录数 | `objective_outcomes.explicit_tool_failures` | 按调用本身保存的失败状态计数，供回看客观失败记录而不判断整个任务成败。 | 部分 |
| 验证命令线索 | `validation_command_candidates` | 当命令信息完整时，数出可能在运行测试、检查或构建的操作。 | 待数据 |
| 验证覆盖范围 | `validation_scope` | 说明检查的是局部内容还是完整项目，目前没有足够证据时保持未知。 | 待数据 |
| 正负反馈候选 | `subjective_outcome_candidates` | 找出同一任务的明确交付之后，人说“可以了”或“还是不行”等直接反馈的记录。 | 部分 |
| 任务是否成功 | `task_success` | 预留整个任务是否成功的结果，但当前不会根据助手宣称完成或用户沉默来填写。 | 待数据 |
| 各模型的请求分布 | `usage.models` | 按每次真实请求所使用的模型，统计各模型被调用了多少次。 | 待数据 |
| token 各分项 | `token_buckets` | 分别列出未缓存输入、缓存读取、缓存写入和输出各消耗了多少 token。 | 待数据 |
| 已知请求的 token 小计 | `known_call_tokens` | 只把信息完整且覆盖明确的请求用量相加，不把这个小计冒充全部用量。 | 待数据 |
| 无法采用的请求记录数 | `invalid_request_rows` | 数出有记录但不满足逐次请求计量条件的模型记录有多少条。 | 待数据 |
| 可用累计快照 | `cumulative_snapshots` | 在计数周期和覆盖范围明确时，保留同一口径最后可信的一份累计用量。 | 待数据 |
| 旧格式末次用量报告 | `legacy_latest_reports` | 原样保留各会话最后记录的累计用量报告，但不把不同报告相加成全局总量。 | 部分 |
| 累计计数回退异常 | `cumulative_regressed_keys` | 当同一计数周期的累计用量反而变小时，标出异常并停止把它当作可信总量。 | 待数据 |
| 费用来源与价目版本 | `cost_sources` / `price_table_versions` | 说明费用是原生报告还是按哪一版价目表计算出来的。 | 待数据 |
| 分出了多少组 | `clustering.cluster_count` | 统计当前有效文本被分成了多少个组，不预先强行规定组数。 | 部分 |
| 没有归组的点数 | `clustering.noise_count` | 统计有多少份有效文本在当前距离规则下没有足够接近的伙伴。 | 部分 |
| 每组包含多少会话 | `clusters[].size` | 统计每个文本组里有多少个有效会话。 | 部分 |
| 每组的代表性片段 | `clusters[].top_terms` | 分别列出每个文本组里相对有代表性的短片段，而不自动给组起主题名。 | 部分 |
| 新颖度比较用了多少历史样本 | `earlier_n` | 说明计算当前文本的不同程度时，实际能拿来比较的更早会话有多少个。 | 部分 |
| 常见语言或文件类型 | `top_languages` | 汇总各会话中明确出现的文件扩展名线索，看哪些语言或文件类型更常被提到。 | 部分 |

## 十、判断这些数字能不能信的配套信息

这些不是用户特征，但看任何结果时都应该一起看。

| 信息 | 字段 | 一句话说明 |
| --- | --- | --- |
| 本次分析范围 | `scope` | 说明这次选了哪些项目、会话、时间、显示时区和排除项。 |
| 当前结果的覆盖情况 | `coverage` | 说明每类数据是完整可读、只读到部分、根本不可用，还是被主动排除。 |
| 原始输入的覆盖情况 | `source_coverage` | 说明进入分析前的整批台账本身有哪些能力和缺口。 |
| 有效样本量 | `effective_samples` / `effective_n` | 说明某个结果实际用了多少个会话、消息或调用。 |
| 未知数量 | `unknown_counts` / `unknown_n` | 说明有多少条记录因为来源、时间、轮次或状态不明而不能支持对应判断。 |
| 文本长度测量质量 | `text_measurements` | 说明消息长度来自完整统计还是截断后的下界，并列出各自的可用数量。 |
| 提示词结构测量质量 | `prompt_structure[].quality` | 说明结构数量来自规范化正文还是只保留了部分文字。 |
| 耗时来源和质量 | `duration_source` / `duration_quality` | 说明耗时是原生报告、可靠端点计算，还是日志时间差估算。 |
| 耗时有效数和未知数 | `duration_effective_n` / `duration_unknown_n` | 说明有多少次调用能提供耗时，以及多少次没有可用耗时。 |
| 可靠区间数和缺失数 | `reliable_interval_n` / `interval_unavailable_n` | 说明有多少次调用具备可靠起止时间，以及多少次不能参与区间合并。 |
| 日期统计有效数和缺时数 | `activity_rhythm.*.effective_n` / `time_unknown_n` | 说明日期分布实际纳入了多少条记录，又有多少条因为缺时间而被排除。 |
| token 完整和未知请求数 | `token_complete_call_n` / `token_unknown_call_n` | 说明多少次请求具备完整 token 分项，多少次仍缺必要分项。 |
| 费用和时延有效样本量 | `cost_effective_n` / `cost_unknown_n` / `latency_effective_n` / `ttft_effective_n` | 说明费用、请求延迟和首字延迟分别有多少条可用证据。 |
| 用量采用的口径 | `total_basis` / `token_bucket_basis` | 说明总量和分项来自逐次请求还是累计快照，避免把不同口径相加。 |
| 聚类运行状态 | `clustering.status` | 说明聚类已经生成结果，还是因为有效文本太少而暂不聚类。 |
| 排除和缺失原因 | `selection` / `reason` | 说明哪些记录因为重复历史、筛选条件或信息不足而没有进入相应结果。 |
| 数据与算法版本 | `versions` / `feature_schema_version` / `vectorizer_version` / `library_versions` | 记录这次结果使用了哪一版输入、解析规则、特征算法和数值库。 |
| 固定样本边界 | `sample_boundary` | 说明历史数据最初导入到哪个截止时间、采用了哪些排除限制。 |
| 本次输入指纹 | `analysis_digest` | 用一个摘要标记本次输入内容、范围和特征版本，方便发现分析条件是否变化。 |
| 证据定位 | `human_evidence_ids` / `event_uid` / `call_uid` | 让你能回到对应的消息或工具记录核对某个数字是怎么来的。 |
