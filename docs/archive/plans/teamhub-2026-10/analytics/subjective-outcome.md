## 范围

这里只记录用户明确表达的评价。用户沉默、会话结束、助手说“已完成”，都不足以判断用户接受了结果；测试通过属于客观结果，也不在本族内。实际有没有使用、长期是否满意，留待后续研究。交付过程中的即时纠偏见 [Interaction](<interaction.md>)。

当前采用本地规则识别明确的中英文表达，不调用模型。只使用能确认是真人直接发出的主会话消息；引用、示例、假设、提问和来源不明的消息不会直接算成用户反馈。

## 特征口径

| 字段 | 记录什么 | 怎么判断，缺信息怎么办 |
| --- | --- | --- |
| `user_acceptance` | 每条反馈的接受状态：接受、拒收、混合或未知。 | 匹配明确表达；同一条里既肯定又否定时保留混合。“谢谢”“算了”本身不足以判断。 |
| `user_confirmed_completion` | 对反馈对象的完成确认：是、否或未知。 | 与接受分开记录。接受一版回复不等于任务结束；同一条消息里相互矛盾的完成陈述保留未知，并标记冲突。 |
| `rework_feedback` | 一条或多条返工要求，以及各自的原因。 | 识别明确重写、重做等要求；只提取同一句里直接说明的原因，没说就留空。单纯新增要求不算返工。 |
| `feedback_target` | 对应的会话、任务、交付事件、产物和版本。 | 优先使用明确引用，否则查同一任务此前最近的交付；对象或版本不清楚时保留候选。无效引用不能改连到其他交付。 |
| `feedback_evidence` | 消息 ID、脱敏后的证据片段、事件顺序和时间。 | 通过 ID 回查原消息；缺时间戳就保留顺序，不补造时间。输出片段不包含完整原始日志。 |
| `delivery_states` | 每份交付的反馈历史和各维度的最新状态。 | 按顺序保留多次反馈；新版本单独记录，没有反馈就保持未知。 |

汇总按**已关联到对象的反馈消息**计数。同一个人评价两次，就是两条观察，不能当成两个成功任务。无法确认的反馈和没有收到反馈的交付会另外列出，避免把它们算成好评或差评；这些计数不直接换算成满意率。

## 分析函数

处理分三步：先找出最终回复和明确反馈，再确认反馈指向哪里，最后保留历史并汇总。每一步都保留证据，无法确认的部分留作候选或未知。

| 已实现函数 | 输入 → 输出 | 主要作用 |
| --- | --- | --- |
| `classify_feedback(text)` | 消息正文 → 接受、完成、返工标签 | 清理引用和平台材料，排除示例、条件等表达，再识别直接反馈。 |
| `collect_deliveries(events, main_ids)` | 事件与主会话列表 → 交付记录 | 找出非空最终回复，兼容当前 `final` 和历史 `final_answer` 标记。 |
| `extract_subjective_feedback(messages, deliveries, main_ids)` | 消息与交付 → 带证据和关联状态的反馈 | 检查真人来源，提取标签、证据和时间，并调用对象关联。 |
| `link_feedback_targets(feedback, deliveries)` | 反馈与交付 → 对象、版本和关联状态 | 检查同会话、先后顺序、任务及版本，避免把反馈连错对象。 |
| `summarize_subjective_outcomes(feedback, deliveries, ...)` | 反馈、交付与覆盖信息 → 计数和历史 | 汇总能确认的反馈，另列候选和未反馈交付。 |
| `analyze_subjective_outcomes(events, main_ids, event_status)` | 筛选后的事件 → 本族完整结果 | 串联提取、关联和汇总，说明本次数据能覆盖多少。 |
| `aggregate_subjective_outcomes(reports, event_status)` | 会话结果 → 项目和概览计数 | 复用会话结果，保证不同入口的统计一致。 |

反馈只关联同一会话里更早的交付。仅说“上一版”而缺少版本信息时不会猜；旧数据库推导出的任务 ID 也只支持候选关联。时间筛选包含起点、不包含终点；如果交付在筛选范围之外，反馈保持未关联，不自动补入范围外的历史。

## 验收样例

下列例子都假设消息来源可以确认，交付对象也有足够依据。

| 输入情境 | 预期结果 |
| --- | --- |
| 交付 A 后，用户说“这个可以了”。 | 记录对 A 的接受；任务是否完成仍要看有没有明确确认。 |
| 用户说“任务已经完成了”，且任务 ID 能可靠关联。 | 记录用户对该任务的完成确认，不扩展到其他任务或整个项目。 |
| 用户说“请重写结论，因为缺少测试结果”。 | 记录返工要求，以及“缺少测试结果”这个明确原因。 |
| 用户先接受 A，后来又说“还是不行，请重写”。 | 两次反馈都保留，A 的最新接受状态更新为拒收；不会删掉先前接受的记录。 |
| A 被接受后，助手又交付了 B，用户没有回复。 | B 的结果未知，不能沿用 A 的接受状态。 |
| 用户让系统分析一句引文：“这个可以了”。 | 引文不作为用户本人对交付的接受。 |

## 补充特征与函数

本轮补充了**交付反馈历史**。只看累计好评、差评，会丢掉“先接受，后返工”的过程；`delivery_states` 因此按交付保存反馈顺序，并给出各维度的最新状态。反馈消息 ID 用于回查证据，事件顺序用于还原变化，新版本从未知状态开始。

这一扩展由 `MistyHuang03` 的本轮需求发起，关联同一 [Issue #4](https://github.com/Orbit-Labs-AI/Orbit-Source/issues/4) 和 [PR #17](https://github.com/Orbit-Labs-AI/Orbit-Source/pull/17)。`summarize_subjective_outcomes` 负责生成历史，入口与聚合函数负责接入已有分析；状态反转、未反馈和版本隔离均已测试，团队口径确认仍待完成。

## 真实数据表现

本次沿用截至 **2026-10-01 23:43:13（Asia/Shanghai）** 的已有快照和一个排除项。重新解析了 36 份日志、41,740 个事件，按原策略筛选后分析 35 个会话、40,664 个事件。

## 讨论与下一步

- **先补真实反馈样本。** 在有授权的前提下收集正负反馈，由人工独立标注评价内容、对象和版本，再统计误报、漏报及关联准确率。
- **补可靠的任务和产物信息。** 与 Task、Respond 对齐任务 ID、交付 ID 和版本，减少“识别到了反馈，却不知道在评价哪一版”的情况。
- **补尚未覆盖的表达。** 当前“任务未完成”“任务还未完成”“问题未解决”会漏检并保持未知。这项 P2 按本轮允许暂缓非 P0/P1 的要求保留待办；后续扩词时同时补正例及否定、引用反例。
- **继续测试复杂情况。** 长文本、含糊指代、跨任务反馈、并发和更大规模处理尚未充分验证。
- **完成团队验收。** 确认明确反馈的范围、返工与新增需求的区别、多次反馈的呈现方式，再勾选开头的 Feature TODO。
