# 今晚先跑通什么

输入是用户授权的本地 Codex 历史记录。输出是一份能回答三个问题的分析：你在协作中明确要求过什么，哪些地方反复需要纠正，下一次可以试哪个写作 skill。每条结论都带可回看的证据；数据不够时直接说明缺什么。

`MistyHuang03` 已确认三位成员同意本次范围。先做标准化、基础画像、瓶颈分析、资源目录、写作 skill 推荐和 evaluation。main 上的 Tandem demo 提供展示语境，里面的示例数字和人格权重不作为真实数据或模型。

## 第一版的数据流

```
Codex JSONL（只读） → 统一事件 → SQLite → 证据分析 → 中文结果与 skill 建议
                                                 ↓
                                           场景 evaluation
```

| 模块 | 它负责什么 | 为什么现在需要 |
| --- | --- | --- |
| importers/codex | 按实际格式读取会话，区分用户与自动审批记录 | 混入审批转录会形成假的用户画像 |
| models / store | 保存事件、项目、模型、来源和导入状态 | 同一记录重复导入不能变成新证据 |
| feedback / analysis | 区分要求、纠正和接受；统计证据覆盖 | 需要知道结论究竟来自哪里 |
| narrative | 先讲发现，再给证据与下一步 | 开发者和使用者都要读得懂结果 |
| catalog / recommend | 记录来源、版本、适用场景；匹配写作需要 | 推荐应针对问题，而非按星数排序 |
| evaluation | 检查事实、场景、表达和误判 | 自动评分只是检查工具，不能代替用户验收 |
| cli / api | 提供复现命令和后续前端接口 | 团队需要独立跑通同一条流程 |

先用 Python 流式读取和 SQLite。只有运行结果暴露出明确需要，才增加 Polars、DuckDB、向量检索或模型；选型依据与来源单独记录。各层用普通函数连接，不建立通用插件框架。

## 数据和评价分开

这次开发开始前的历史作为样本；本次会话、开发后新生成的审批记录不进入画像。用户这次补充的验收标准单独留在评价区，不能伪装成历史反馈。仓库只保存人工构造的测试样本、代码与报告，不提交真实聊天、个人路径或密钥。

基础画像先描述有证据的协作要求，不把一次要求变成长期人格。反馈比例按会话计数，并报告样本数；同一个任务中的重复要求不能当成多个独立人的认可。首版不估计未知的用户理想转移分布，也不把公式写成已经取得的效果。

## 迭代顺序

1. v0.1：最小闭环、可复现的合成场景、首次真实历史导入。
2. 依据误判和读者评价修正解析、证据和表达；每个跑通版本提交推送，附报告。
3. 增加有必要的来源核对、场景覆盖与推荐对照；以留出样本检查效果。
4. 时间窗口结束前留下独立验收入口、实际结果、PR 与仍需人工判断的部分。
