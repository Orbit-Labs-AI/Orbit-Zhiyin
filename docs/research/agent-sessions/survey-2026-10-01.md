# 主流Agent本地轨迹数据调研报告

如何处理这些记录，见[agent轨迹数据处理方向与分析工具](<../trajectory-modeling/processing-methods.md>)：包含数学建模、算法验证、工具选型、时间分析、四轴画像及 skill 推荐准备。

依据是官方文档和官方源码；源码链接固定到本次查看的提交。**这是一份资料与源码调研，没有逐个安装实测，也没有读取、收集本机的原始聊天记录。** 默认分支中的新实现可能尚未进入用户安装的稳定版，接入时必须记录实际版本并检查样本。产品方案属于 AI 建议，尚非团队决定。

## 1. 先看结论

**大多数编码 agent 已经留下足够的数据，用来分析“用户怎么与 agent 协作、经常卡在哪一步”。但本地聊天记录通常无法单独回答“结果好不好、用户实际花了多久、换个策略会不会更好”。**

最有价值的现成数据是：用户指令、模型回复、工具调用与结果、模型及 token 用量、上下文压缩、分支和子 agent 关系。最常缺失的是：精确等待时间、完整审批过程、人工修改、独立验收结果和实际账单。

对 Hackathon 项目，建议先做三件事：

1. **读已有轨迹，展示带证据的协作习惯。** 例如“最近 8 次文档任务中，有 5 次明确要求简洁”，并能点回对应指令。
2. **定位可观察的卡点。** 例如同一测试连续失败、反复读取同一文件、压缩后用户再次补充相同约束。
3. **补采缺失信号，再评估改进。** 用 hooks 或事件接口记录等待与审批，用测试或用户确认记录是否达标。

接入难度主要来自各工具的记录口径不同，而非缺少数据。尤其要分清：**提示词历史、完整会话、模型实际看到的上下文、实时事件、统计缓存，是五种不同的数据。**

## 2. 本地通常保存哪几类数据

| 数据类型 | 常见内容 | 可以拿来做什么 | 容易误读的地方 |
| --- | --- | --- | --- |
| 会话与执行记录 | 用户消息、模型回复、工具参数／结果、错误、时间戳 | 复盘、纠正点识别、工具使用统计 | 一个消息块不一定等于一次模型请求 |
| 会话元数据 | 工作目录、会话 ID、父会话、模型、版本、Git 分支 | 按项目与任务归类、连接子 agent | 一个会话可能跨多个任务，多个会话也可能属于同一任务 |
| 配置、规则与记忆 | 权限模式、MCP、skills、项目指令、自动记忆 | 解释工作环境、记录显式偏好 | 配置存在不代表本次使用；AI 记忆也可能有误 |
| 文件变化与检查点 | diff、修改前快照、影子 Git、计划文件 | 观察返工与回退、关联产物 | 通常不能重建依赖、网络服务、外部状态等完整环境 |
| 诊断与遥测 | 调试日志、请求失败、工具耗时、用量事件 | 排障、等待时间分解 | 有些要主动开启；实时发出的事件不一定落盘 |
| 汇总与派生缓存 | token／费用汇总、会话搜索库、洞察报告 | 快速索引、粗粒度趋势 | 与原始记录重叠，不能当作第二份活动重复累计 |

图片、附件和大段工具输出还可能另存文件，轨迹里只留下引用或截断后的内容。采集器要同时记录“内容是否完整”，不能把缺失当成空白。

## 3. 各工具保存在哪里，能读到什么

以下是常见默认位置。`~` 指运行 agent 的用户主目录；远程 SSH、容器、WSL 的“本地”通常指远端运行环境。自定义 home、数据目录、编辑器版本及配置均可能改变位置。表中的能力以各小节引用为依据。

| 工具与形态 | 主要轨迹位置／入口 | 现成数据重点 | 接入时最应注意 |
| --- | --- | --- | --- |
| Codex 本地 CLI／app-server | `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`；另有 `archived_sessions/`；`thread/read` 等接口 | 对话、工具、上下文、用量、父子线程 | `history.jsonl` 只是输入历史；部分实时事件被过滤 |
| Claude Code | `~/.claude/projects/<项目编码>/<session>.jsonl` | 对话、工具、请求关联、子 agent、记忆／快照 | 同一响应可拆成多条；原始 schema 非稳定公开协议 |
| Pi 标准 coding agent | `~/.pi/agent/sessions/--<目录编码>--/<时间>_<id>.jsonl` | 对话树、模型、用量与估算费用、压缩／分支 | 文件包含多条分支；当前上下文不是全部历史 |
| OpenCode | 通常 `~/.local/share/opencode/opencode.db`；`opencode db path`、`opencode export` | 会话、消息分块、工具状态／耗时、用量、文件变化 | 当前源码以 SQLite 为主；数据库行不是完整事件流 |
| Gemini CLI | `~/.gemini/tmp/<project_hash>/chats/` | 对话、工具、模型、token、压缩／摘要 | 新源码写 JSONL，旧版有 JSON；需重放更新与回退 |
| Cursor 编辑器 Agent | 通过 hook 的 `transcript_path` 获取；子 agent 有独立路径 | 开启 transcript 后的记录；hooks 提供工具、耗时、压缩等 | 未启用 transcript 时路径可为空；不硬编码内部数据库 |
| Cline／Roo Code 的 VS Code 扩展 | `<编辑器 globalStorage>/<扩展ID>/tasks/<taskId>/` | API 历史、UI 消息、任务元数据、用量／错误 | API 与 UI 记录相互重叠；不同扩展／版本分别适配 |
| GitHub Copilot CLI | `~/.copilot/session-state/<id>/events.jsonl`；`session-store.db` 为派生索引 | 消息、工具生命周期、审批、子 agent、skills、压缩 | 逐请求 usage 是临时事件；本地运行可同时同步云端 |
| Aider | 项目目录 `.aider.chat.history.md`、`.aider.input.history` | 对话、输入历史、代码变化；可关联 Git | 全量 LLM 历史需另开；默认不是结构化执行日志 |

### 3.1 Codex：rollout 才是轨迹主体

`CODEX_HOME` 默认是 `~/.codex`。除了会话，目录里还有配置、认证、日志和缓存；应从会话入口读数据，避免整目录打包。[官方配置文档](https://developers.openai.com/codex/config-advanced/)

源码确认了两个不同文件用途：

- **`history.jsonl`：输入回忆。** 主要字段是 `session_id`、`ts`、`text`，供终端翻查输入；关闭 `history.persistence` 不能据此推断所有会话轨迹都停止保存。[输入历史源码](https://github.com/openai/codex/blob/444da310e108da16aaeb18fd790b0ac464f08aca/codex-rs/message-history/src/lib.rs)
- **rollout：会话轨迹。** 可包含会话元数据、消息、工具调用及返回、turn 上下文、压缩和 token 用量。源码按日期组织文件，也处理归档、压缩和不同历史模式。[存储实现](https://github.com/openai/codex/blob/444da310e108da16aaeb18fd790b0ac464f08aca/codex-rs/rollout/src/recorder.rs)

适合提取：任务指令与纠正、工具链、工作目录、模型与推理配置、输入／缓存／输出用量、压缩与回退、父子线程关系。用量需区分单次增量与线程累计值，不能全部相加。

**精确耗时与审批不能默认从历史文件恢复。** 本次源码的持久化策略会过滤 `ExecCommandBegin/End`、流式输出、审批请求等部分事件；已完成 item 或工具输出可能保留部分信息，但不保证每次执行都有起止时间。[持久化策略](https://github.com/openai/codex/blob/444da310e108da16aaeb18fd790b0ac464f08aca/codex-rs/rollout/src/policy.rs)

建议优先用 `thread/read`、会话／turn 查询接口读取结构，再做按版本的文件解析兜底。分页接口的稳定性与可用性须按版本检查；临时线程也可能不落盘。**接口发出的事件数量，不等于磁盘记录数量。** [app-server 文档](https://developers.openai.com/codex/app-server/)

### 3.2 Claude Code：会话、子 agent、快照与记忆都很有用

主轨迹是项目目录下的会话 JSONL。子 agent 在对应会话的 `subagents/`；超大工具结果在 `tool-results/`。另有 `file-history/` 修改前快照、`plans/`、项目 `memory/`。`history.jsonl` 是输入历史，`stats-cache.json`、`usage-data/` 是统计或派生分析；调试日志需开启 debug。官方文档当前给出的会话默认保留期为 30 天，可配置。[本地目录说明](https://code.claude.com/docs/en/claude-directory)

轨迹可用于关联用户／助手消息、工具调用与结果、请求和消息链；模型用量以实际版本中可用字段为准。官方明确提醒：原始 transcript 格式会变；一个 API 响应可能按内容块拆成多条，`uuid`、`parentUuid`、`requestId` 的含义也要按版本处理。不能直接把 assistant 行数当成请求数。[用量与记录关联说明](https://code.claude.com/docs/en/monitoring-usage)

只读展示优先使用 Agent SDK 的 `list_sessions()`、`get_session_messages()`；它们读取本地文件、重建消息链，与 CLI 的会话目录相通。它们适合会话浏览，深度统计仍需核验原始字段。[官方会话浏览示例](https://platform.claude.com/cookbook/claude-agent-sdk-05-building-a-session-browser)

精确工具耗时、审批拒绝和 API 失败可补采 hooks 或官方 OpenTelemetry 事件；需要配置记录器／导出器，不能假设已经存在本地历史数据。[Hooks](https://code.claude.com/docs/en/hooks)、[OpenTelemetry 监控](https://code.claude.com/docs/en/monitoring-usage)

费用也要分清口径：headless 的 `total_cost_usd` 是客户端估算，恢复会话后的结果可能包含之前运行的累计费用。会话还可在特定模式下禁用持久化，因此“没找到文件”不等于用户没有使用。[Headless 输出](https://code.claude.com/docs/en/headless)、[CLI 参数](https://code.claude.com/docs/en/cli-reference)

### 3.3 Pi：结构公开，尤其适合做首版解析器

这里指 Pi 官方标准 coding agent，当前官方仓库为 `earendil-works/pi`；不要把不同 fork 的目录与格式混在一起。

JSONL 条目通过 `id`、`parentId` 构成树。助手消息可有 `provider`、`model`、`usage`、`stopReason`；工具结果有 `toolCallId`、`toolName`、`isError`。用量细分输入、输出、缓存读写及估算费用。系统消息、模型／思考级别变化、压缩、分支摘要、扩展消息也可记录。[会话格式](https://github.com/earendil-works/pi/blob/70c036211de5378508ae2456f3c7ae3cf9f8bc75/packages/coding-agent/docs/session-format.md)、[消息与用量类型](https://github.com/earendil-works/pi/blob/70c036211de5378508ae2456f3c7ae3cf9f8bc75/packages/coding-agent/docs/message-types.md)

接入时有三个重点：

- **看路径，不能只看文件顺序。** 当前分支、曾探索的分支和 fork 继承的历史需要分开。
- **算费用，不能只看 assistant。** 新版独立 `usage` 条目、压缩与分支摘要也可能产生用量；选中的虚拟模型与实际回答的模型可能不同。
- **看原始历史，不代表知道模型当时看到了什么。** 压缩和 `context_edit` 会改变后续上下文，原记录仍保留；工具结果时间戳也不等于标准化执行时长。

Pi 提供 `SessionManager` 导航与上下文重建能力，也支持不落盘的内存会话。结构透明利于开发，但仍需处理不同版本和扩展产生的未知条目。[SessionManager 实现](https://github.com/earendil-works/pi/blob/70c036211de5378508ae2456f3c7ae3cf9f8bc75/packages/coding-agent/src/core/session-manager.ts)

### 3.4 OpenCode：工具状态和耗时比较直接

常见数据根目录是 `~/.local/share/opencode`。本次源码使用 SQLite，正式渠道默认 `opencode.db`，其他渠道可带后缀，也可通过配置覆盖路径。旧资料中的逐项目 JSON 布局不宜当作现行唯一格式。[数据目录](https://opencode.ai/docs/troubleshooting/)、[数据库实现](https://github.com/anomalyco/opencode/blob/0112a92c416f5ad833d96e7a8308441f0a875d94/packages/core/src/database/database.ts)

schema 包含消息创建／完成时间、模型与 provider、agent、cost、token／缓存；工具 part 有状态、输入、输出或错误，以及起止时间。还可见步骤、压缩、重试、快照和 patch 等类型，适合分析工具失败、上下文与模型开销。[会话与消息 schema](https://github.com/anomalyco/opencode/blob/0112a92c416f5ad833d96e7a8308441f0a875d94/packages/schema/src/v1/session.ts)

优先使用 `opencode db path` 确认位置、`opencode export <sessionID>` 导出；当前文档也提供脱敏选项，仍需检查输出。数据库可能只保留某个 part 的最终状态，不能当作完整状态变化流；消息与步骤的用量不能重复累计。[CLI 文档](https://opencode.ai/docs/cli/)

### 3.5 Gemini CLI：已有自动记录，解析要兼容迁移

官方文档说明会话自动保存，包含消息、工具调用与结果、模型相关记录及 token；当前默认保留策略为 30 天，可配置。主要目录是 `~/.gemini/tmp/<project_hash>/chats/`。[会话管理](https://geminicli.com/docs/cli/session-management/)

本次源码已经写 JSONL，并兼容旧 JSON。除消息外，还写元数据更新、同 ID 消息更新和 `$rewindTo` 回退记录。需要按顺序重建状态，不能把每行当成新消息。字段包括消息 ID／时间、工具参数／结果／状态、model，以及 input／output／cached／thoughts／tool／total token；不是每条都有，也不能把所有分项与 total 再相加。[记录器](https://github.com/google-gemini/gemini-cli/blob/c6bccb7ecbf6d8368d995455dd725ed34466faad/packages/core/src/services/chatRecordingService.ts)、[记录类型](https://github.com/google-gemini/gemini-cli/blob/c6bccb7ecbf6d8368d995455dd725ed34466faad/packages/core/src/services/chatRecordingTypes.ts)

文件恢复能力需另看 checkpoint：它默认关闭，开启后才有影子 Git、修改前对话及待执行工具记录。没有 checkpoint 时，不能声称可以完整重放文件状态。[Checkpointing](https://geminicli.com/docs/cli/checkpointing/)

### 3.6 Cursor：用官方 hooks 获取路径和补采事件

官方 hooks 提供 `conversation_id`、`generation_id`、模型配置、版本、工作目录与 `transcript_path`。transcript 关闭时路径可为空；子 agent 的 transcript 路径可单独提供。工具 hooks 可带调用 ID、输入／输出、失败类型和耗时；压缩 hook 可给出上下文占用。部分工具耗时明确不含审批等待，统计时需另分段。[Hooks 文档](https://cursor.com/docs/hooks)

因此优先按官方返回的路径读取已启用记录，再用 hooks 写自己的结构化事件。**本次官方资料不足以确认所有 Cursor 安装的固定历史目录与内部数据库 schema**，不把社区常见路径写成可靠接口。编辑器、CLI 和远程 Agent 也应分别验证。

### 3.7 Cline／Roo Code：同时有 API 历史和 UI 历史

Cline 的持久化实现把任务放在扩展 `globalStorage` 的 `tasks/<id>/` 中，包含 `api_conversation_history.json`、`ui_messages.json`、`context_history.json`、`task_metadata.json`。元数据可记录上下文文件、模型使用、环境变化；UI 消息可记录用户反馈、审批询问、命令输出、请求失败及 token／缓存／费用。[任务存储](https://github.com/cline/cline/blob/8eee168b80127b0c94bad849323754b5864865e7/apps/vscode/src/core/storage/disk.ts)、[UI 消息类型](https://github.com/cline/cline/blob/8eee168b80127b0c94bad849323754b5864865e7/apps/vscode/src/shared/ExtensionMessage.ts)

例如 macOS 官方 VS Code 的 Cline 扩展常见位置为 `~/Library/Application Support/Code/User/globalStorage/saoudrizwan.claude-dev/tasks/`；编辑器变体、Profiles、远程扩展和新运行形态可能不同，应读取宿主实际提供的存储路径。[扩展标识](https://github.com/cline/cline/blob/8eee168b80127b0c94bad849323754b5864865e7/apps/vscode/package.json)

Roo Code 也保留 API 历史、UI 消息与任务元数据，另有历史条目／索引。两者有共同来源，但不能直接假设字段、统计口径和新版本布局完全一致。[Roo 持久化实现](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task-persistence/apiMessages.ts)、[文件名定义](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/shared/globalFileNames.ts)

API 历史适合重建模型对话，UI 历史适合找人机交互。**它们是同一任务的不同视图，不能各算一次任务／请求。** 部分消息会原地更新、压缩或截断；扩展存储也不等于所有 CLI／SDK 形态的存储。

### 3.8 Copilot CLI：执行事件丰富，但逐请求用量有缺口

`~/.copilot/session-state/<id>/events.jsonl` 是主轨迹，旁边可有计划、检查点和文件跟踪记录。`session-store.db` 保存部分数据用于查询，`command-history-state/` 是输入历史，`logs/` 是诊断日志；根目录可配置。[配置目录](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-config-dir-reference)

持久化事件覆盖模型 turn、消息、工具起止／结果、审批、错误、压缩、子 agent 和 skill 调用。可用 ID 关联调用，并从时间戳分析执行跨度。[事件参考](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/streaming-events)

需要特别分清：`assistant.usage` 的逐请求模型用量／耗时是临时事件，默认不写事件文件；持久化的 `session.usage_checkpoint`、`session.shutdown` 可提供累计账务或模型汇总，两者不可混算。`session.idle` 也不落盘，`session.task_complete` 是模型的完成声明。要做细粒度成本与延迟分析，需订阅并保存实时事件；完成声明还需独立验收。[事件参考](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/streaming-events)、[Agent Loop](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/agent-loop)

Copilot CLI 的本地会话当前默认可同步到账户，企业策略可限制同步；IDE 中 Copilot 的存储由 IDE 决定。不能把“本机有文件”理解成“数据从未离开本机”。[会话数据说明](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/session-data)

### 3.9 Aider：默认适合文本复盘，细粒度分析需补采

默认保存 `.aider.input.history` 和 `.aider.chat.history.md`；`--llm-history-file` 可另外记录 LLM 输入／输出，但默认未设置。文件位置可改，`--restore-chat-history` 控制恢复历史，不代表默认没有记录。[官方参数](https://aider.chat/docs/config/options.html)

可提取用户指令、回复与代码变化，结合 Git 查看产物；但 Markdown 历史没有统一的调用 ID、工具生命周期或完整用量 schema。适合先做文本层面的习惯／纠正分析，精确请求成本、等待分解与操作链需要补采。

## 4. 能做怎样的用户画像

画像应描述**有证据、可修改的协作习惯**。优先提取用户明确说过的要求，再用跨任务记录形成待确认推断；显示适用项目、时间范围和反例。以下是分析设计建议，不是各工具默认生成的结论。

| 画像维度 | 可用证据 | 合适的表达 | 不应直接推断 |
| --- | --- | --- | --- |
| 输出偏好 | 明确要求的语言、篇幅、格式、引用；对输出的纠正 | “近 8 次写作任务中，5 次要求简洁” | 从一次催促判断长期性格 |
| 工作方式 | 先计划／先执行的指令、任务拆分、确认节点 | “在部署任务中通常先看具体方案” | 审批多就是不信任 agent |
| 验收要求 | 用户要求测试、编译、截图、出处、复查 | “代码任务常要求提供验证结果” | 没提测试就是不重视质量 |
| 常见工作场景 | 任务目标、项目、工具与文件类型 | “近期主要处理文档整理与数据分析” | 文件扩展名直接等于能力水平 |
| 协作中的摩擦 | 用户明确纠正、重复约束、停止／重做 | “经常纠正未写入指定目录的问题” | 每次后续消息都是返工或不满意 |
| 工具与模型习惯 | 实际调用、模型变化、skill 调用证据 | “同类任务中常用某工具链” | 安装了 skill 就视为用过，选了模型就视为偏爱 |

先给“观察”，再给“建议”，让用户确认后才进入长期偏好。例如：

> 观察：最近 6 次资料整理中，有 4 次追加“直接写入指定目录”。建议：这类任务默认先确认目标路径并生成文件。证据：4 条原始用户指令。状态：待用户确认。

自动记忆、压缩摘要和 agent 自己的评语可以帮助检索，但应回到原始消息核实。只收到了成功会话、某一个项目或最近 30 天的数据时，画像也只能代表这个范围。

## 5. 能定位哪些瓶颈，需要补什么

| 问题 | 现有轨迹能看什么 | 要补的数据／判断边界 |
| --- | --- | --- |
| 需求反复澄清 | 澄清问题、用户补充、明确纠正 | 区分初始信息不足、正常探索和需求变更 |
| 工具持续失败 | 调用 ID、失败结果、同类重试、退出状态 | 错误可能来自环境／权限；不能全归因于模型 |
| 搜索／阅读重复 | 相近查询、同文件重复读取、工具输出体积 | 重复读取可能是检查新修改；结合文件版本与目标 |
| 上下文压力 | 输入 token 增长、缓存、压缩、回退 | token 与上下文占用不是同一指标；压缩本身不等于故障 |
| 执行很慢 | 有起止时间的工具、模型请求、子 agent | 缺字段时只能给粗略跨度；需补采排队、审批和首 token 时间 |
| 人工介入多 | 审批、明确接管、用户反馈、手工纠正 | 补采实际人工编辑／交互；配置要求的审批不算策略失败 |
| 消耗很高 | 去重后的请求用量、缓存、估算费用 | 订阅／积分／API 账单口径不同；统一标注单位和估算来源 |
| 反复改却未达标 | 修改、回退、测试输出、用户拒绝 | 独立测试、验收标准和最终确认；agent 说完成不够 |
| 多 agent 协作低效 | 父子关系、重复探索、错误、汇总 | 保留依赖和并发区间；并行耗时不能直接相加当总时长 |

推荐给用户看的指标是：**同类任务的达标率、达标前明确纠正次数、可测执行／等待时长、达标任务的模型消耗**。先按任务难度、类型、工具版本和权限条件分组，避免把长任务与短问答放在一个效率排行榜。

时间至少分成三种：从发起到结束的总跨度、agent／工具的执行跨度、用户实际投入时间。前两种可部分观测；第三种不能用“两个消息之间的间隔”冒充。

更换 prompt、模型或 skill 后表现改善，也只能先说明相关变化。要判断改进是否由策略造成，需要相近任务的对照实验；历史轨迹本身不能证明因果。

## 6. 统一解析时最容易踩的坑

1. **按行数算请求。** 流式分块、Claude 内容块、消息更新都会放大数量；按原生 request／response／turn ID 归并，无法确定时标为未知。
2. **把两份视图相加。** API／UI、会话文件／SQLite 索引、原记录／统计缓存是重叠数据，先确定主来源。
3. **重复计算继承历史。** fork、恢复和导入可能复制上下文，甚至重新分配消息 ID；需要父会话与继承边界。内容相同也可能是真实重复请求，不能仅靠文本哈希删除。
4. **混合当前分支与总消耗。** 当前上下文只沿有效分支重建；总消耗还应覆盖确实执行过的其他分支及摘要调用，并排除复制历史。
5. **把累计值全部求和。** 区分单次、turn、会话累计及账务窗口；reasoning／cached token 是否属于其他字段的子集也按 provider 定义处理。
6. **把时间戳差当准确耗时。** 落盘时间、响应完成时间和执行开始时间不一定相同。记录时间来源与精度，缺起止就不制造精确延迟。
7. **假设内容完整。** 工具输出可能截断、溢出到附件、被压缩或删除；保留完整性标记与引用，缺失不计为零。
8. **把结束当验收。** 停止、取消、空闲、模型声明完成、测试通过、用户接受是不同状态。

正在增长的 JSONL 还可能有未写完的末行；数据库可能处于 WAL 模式。采集器应只读、支持增量与重放，使用一致性读取／备份方法，并给出解析覆盖率。不要修改 agent 自己的存储来“清洗”数据。

## 7. 对 Lifeline 项目的接入建议

### 数据流与最小统一格式

建议的数据流：**用户选择会话 → 本地读取与脱敏 → 按 agent 版本解析 → 去重并连接调用 → 保存观察及证据 → 用户确认 → 生成建议 → 对照评估。**

首版不必统一所有内部格式，先保留这些字段；缺少就写未知，不补造：

| 层次 | 建议字段 |
| --- | --- |
| 来源 | agent／版本、运行形态、来源文件或接口、原始记录定位、parser 版本、是否完整 |
| 关系 | project／session／task ID、父 session／agent、branch、message／request／call ID、继承边界 |
| 事件 | 用户指令、模型响应、工具、审批、错误、压缩、修改、验收；时间及其精度 |
| 消耗 | 原生 token 分项、单次或累计标记、provider／实际模型、费用值／单位／估算依据 |
| 结果 | 产物／diff 引用、测试结论、用户接受或拒绝、未完成／取消／未知 |
| 画像条目 | 观察、证据集合、适用范围、反例、置信度、用户是否确认、过期时间 |

“会话”由工具定义，“任务”由用户目标定义。任务可以跨会话，先支持用户合并／拆分，自动识别作为建议。采集字段也应有来源标签：原始事实、规则计算、AI 推断、用户确认。

### 先接哪些工具

- **面向目标用户验证：先接 Codex 和 Claude Code。** 用真实授权样本验证用户是否能看懂画像、是否愿意确认并采用建议。
- **验证解析能力：加入 Pi。** 它的公开格式适合测试分支、压缩、模型变化与费用统计；这不代表应该优先服务 Pi 用户。
- **验证精细执行链：再接 OpenCode 或 Copilot CLI。** 前者有工具状态时间，后者有丰富持久化事件，但逐请求用量仍需实时补采。
- Cursor、Cline／Roo、Gemini CLI 与 Aider 按用户实际使用比例加入，避免首版同时维护全部适配器。

### 现有日志与实时采集怎么搭配

**离线导入负责历史复盘，实时采集负责补洞。** 仅为读取已有 CLI 历史，不必先部署模型网关或要求用户把所有 agent 改写成某个 SDK。

需要补采时，优先用各工具官方 hooks、事件订阅或 OpenTelemetry；记录模型与工具起止、审批等待、失败类型、子 agent 关系。SDK 适合接入自己控制的运行流程，不自动覆盖用户之前在其他界面产生的历史。

界面应告诉用户：“本次解析了哪些来源、覆盖哪些字段、缺少什么、结论依据是什么”。画像卡片支持修改与撤回；瓶颈卡片支持回看调用链；策略建议应用后能观察前后变化。可与 Agent协作画像与Lifeline项目介绍（团队讨论／知识库来源，未随本文公开）、OpenTelemetry调研综述（团队讨论／知识库来源，未随本文公开） 中的方案对接。

### 黑客松前准备与验收

| 准备项 | 最小交付物 |
| --- | --- |
| 确定目标用户 | 记录其实际 agent、版本、运行位置及想解决的协作问题 |
| 准备授权样本 | 普通工具任务、明确纠正、工具失败、恢复／fork、压缩、子 agent、取消；合成数据与真实数据分开 |
| 做两种解析器 | Codex／Claude Code 中至少一个，加 Pi；保留原始记录定位与缺失字段 |
| 人工核对统计 | 每个样本手工核对请求／工具数、分支、用量；避免重复计数，展示无法核对之处 |
| 准备结果标准 | 为演示任务定义产物要求、测试或人工验收；保存实际是否达标 |
| 准备演示链路 | 导入 → 证据卡片 → 用户确认偏好 → 策略应用 → 同类任务比较 |

首版验收建议：同一批文件重复导入不会增加活动数；恢复／fork 不重复计入继承消耗；未知版本不会静默算错；每条画像能回到证据；失败能区分工具／环境／审批／结果不合格；费用明确标注估算或原生账务单位。

## 8. 数据处理边界

这是采集实现的必要边界：

- 让用户选择工具、项目、会话和时间段；不默认递归扫描整个主目录。
- 原始轨迹可能含源码、命令输出、粘贴内容和附件。本地先解析，上传前预览与脱敏；认证文件、密钥、cookie、环境变量凭据不进入画像数据。
- Git 配置、邮箱、绝对目录等身份信息通常不需要；项目关联使用匿名 ID，原始定位留在本机。
- 配置／规则仅按允许字段读取；带有凭据的 MCP 配置不应整文件收集。
- 支持撤回导入、删除派生画像与缓存，并说明保留期。不要让上游删除的聊天记录在采集器中永久存活。

最终产品应持续回答三个问题：**这条结论从哪来？缺了哪些数据？用户能否纠正它？** 能回答这三件事，已有本地轨迹就足够支撑一个可信的首版。
