# 从历史轨迹学习可复用技能

本轮要补的能力是从已发生的操作中归纳方法，并在相关任务出现时提供该方法。仅按失败次数推荐一个工具，不能替代这一过程。本文记录采用的已有思想和 Orbit 的简化方向；实现与实验状态见[评测协议](../plans/history-skill-learning.md)。

## 已核对的一手工作

| 工作 | 可借鉴机制 | 本轮边界 |
| --- | --- | --- |
| [Agent Workflow Memory](https://arxiv.org/html/2409.07429v1) | 从一个或多个经历抽取常用子流程；用目标描述和步骤表示，并把实例中的具体值替换成变量 | 只用 offline induction；不在 test 期间把新轨迹写回技能库。Markdown 步骤保留条件、动作与验证，不复现网页操作环境 |
| [ExpeL](https://arxiv.org/html/2308.10144v3) | 汇总成功与失败经验形成可检索的文字知识，把经验提炼与推理阶段的使用分开 | 将“工具调用成功”“任务最终成功”和“模型自称完成”分开记录；没有已知结果就保留未知，不凭空给经验加正面标签 |
| [Voyager](https://arxiv.org/html/2305.16291v2) | 技能库、技能检索、环境反馈及验证共同构成持续改进过程 | 采用库与检索分离、保留来源及验证结果的思想；不引入 Minecraft 的课程学习，也不让推荐自动执行未经审核的代码 |

三项工作均不能保证当前模型、任务或样本量上的收益。这里借鉴的是机制，效果仍以本轮冻结后的配对结果为准。

## 针对当前根因的设计约束

1. **输入保留过程。** 学习材料包含任务目标、工具参数、结果和校验动作的有界片段；不能只保留 `python3` 这样的命令头。材料来自用户明确选择的历史会话，不混入候选任务的 verifier、参考解或 test 轨迹。
2. **跨会话归纳。** 一个候选引用支持它的 session / event ID，重复会话不重复计数。候选可表达技能、规则、检查或流程；没有证据就不为了凑类型生成 MCP 或子代理。
3. **技能有完整边界。** 必须说明何时适用、何时不适用、执行顺序、所需工具、参数占位、终止和验证条件。输出不能固化实例答案或仅给泛泛提醒。
4. **生成与检索分开。** 离线提炼得到候选库；新任务只从冻结库检索。兼容性应由具体内容、所需工具和适配器能力判断，并保留未知状态，不能将目录的 Agent 标签缺失直接等同于不兼容。
5. **验证后选择。** 用 validation 检查候选对成功率、token 和实际行为的影响；内容版本与反馈绑定。未被实际使用的候选不能宣称有效，失败候选也不能通过改名摆脱负面记录。
6. **完整成本。** 候选提炼、验证及检索的模型成本独立于 online task 统计，最终同时给出摊销前后的比较。

## 需要验证的假设

- 当前 12 条 history 的主要问题是否是表示丢失，而不是会话数量本身？比较完整轨迹与现有汇总输入，并按独立历史会话数量消融。
- 目录过滤和列表名额是否解释了全部损失？分别控制兼容标签、证据阈值、top-k、去重与每问题名额，不把多项变化的收益归给其中一项。
- Skill 只列在可用资源中是否足够？分别观测注入、读取和后续方法使用，并比较显式触发要求与仅 description。
- 完整 bundle 是否比单个 Skill 更好？收益和额外上下文、Hook 调用开销一起计算；未触发的 Hook 不得解释 token 降低。

上述参数和实现只能依据 history / validation 改动。最终 test 的失败用于报告局限，不能反向进入本轮算法。
