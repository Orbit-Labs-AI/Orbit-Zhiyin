# 后端怎么工作

默认入口已经切换到统一 L0–L3。当前模块边界、macOS App 接入、存储位置、分页与兼容方式见 [数据流程](data-pipeline.md)；本文其余部分解释报告与评价算法。

先看 `application/reports.py`：它组织画像、推荐和报告，`cli/commands.py` 与 `api/routes.py` 共用该入口。当前完整职责表见 [模块接入表](module-map.md)。

| 模块 | 必须回答的问题 |
| --- | --- |
| `packages/data / data_access` | 从归档生成统一事件和派生表，以只读契约供 App 与分析消费 |
| `legacy / privacy / models` | 保留旧库和历史评价兼容，不承担默认来源获取 |
| `profiling/feedback / bottlenecks / analysis / portrait` | 明确要求是什么，怎样形成画像与可回看的案卷？ |
| `profiling/trajectory` | 修改前后是否有正文和相对评价，哪些证据还不能用于学习？ |
| `recommendation/resource_fetch / catalog` | 资源来自哪里，核对的是哪个版本？ |
| `recommendation/recommend` | 画像、事件、场景、语言是否共同支持一次试用？ |
| `reporting/analysis_reports / narrative` | 中间推导怎样展示，推荐的依据和下一步在哪里？ |
| `evaluation/readability / pipeline / reader` | 规则有没有误判，事实有没有丢，读者能否理解？ |
| `cli / api` | 团队怎样复跑，前端怎样接入同一逻辑？ |
| `analytics/inputs / features / text / service` | 目标契约与旧库怎样分开，哪些测量可用，哪些必须保持未知？ |

新的 Feature Analytics 入口与旧画像分析并存。`analytics` CLI 和 `/v1/analytics/*` 共用无缓存的测量引擎，支持严格范围、覆盖、工具/流程/节律、文本表示与二维坐标。输入映射、真实案例、特征字典与待补字段见 [Feature Analytics MVP](../modules/analytics/feature-analytics.md)。

项目目前按会话工作目录分组，没有足够元数据把所有目录可靠地合成 Git 仓库。数学计算的含义与假设见 [建模说明](../modules/analytics/modeling.md)。下面是接口与数据边界的细节。

下面保留旧库兼容模型与报告规则的说明；原生来源、完整归档和 canonical 发布以 [数据流程](data-pipeline.md) 为准，不能将旧库字段限制套用到默认数据层。

旧库兼容读取器把 Codex 的 `session_meta`、`turn_context`、`response_item`、`event_msg` 整理成会话和事件。用户消息、助手消息、工具调用、工具返回、轮次边界、累计 token 各有类型。角色与原始行号分开保存；消息镜像不能重复计数。

桌面问答回执只提取 `answer`，不把 AI 的 `question` 当作用户要求。正式消息与界面镜像按同轮、同角色、完整内容哈希核对；不同内容的临时补充仍保留。`input_format` 区分直接输入和回执。

用户消息里的代码与引用通过 CommonMark 的源行范围排除，合法列表段落仍保留。固定快照不复制没有历史时间依据的桌面标题或模型；来源类型仍用于排除自动记录。

旧 MVP 数据库只保存需要的字段。每次导入一份文件，在同一事务中替换它的派生记录；文件未变则跳过。修改来源文件的程序中断，不会把已保存记录写成半份。工具参数和完整工具输出经常包含大段私有材料，首版不保存它们。

工具状态只认明确的返回协议。`status_scope` 区分命令退出、脚本错误和包装里的命令结果；包装内返回带已知数量、失败数量和未知数量。stdout 不参与状态判断。旧格式缺完整元数据时保持未知；失败统计描述返回记录，不等于失败原因或浪费时间。

`sample_policies` 按 Codex 数据目录保存快照与排除名单，省略参数仍沿用。扩大范围需显式重设；收紧范围先移除旧派生记录，防止中断后旧范围继续参与分析。`details.ledger_sample_policies` 描述台账输入边界，`details.scope` 描述这次查询筛选，二者分开。

分析层先判断要求作用于说明还是工作流程，再把要求与后续响应、说明修改、连续工具失败关联。`bottlenecks.py` 保存候选问题与上下文，不把它们自动认定为失败或浪费。推荐必须同时有画像证据、瓶颈证据和适用场景；表达层只把这些事实整理成中文。

`feedback.task_contexts` 保留数学讲解、开发报告、文档写作、代码协作和一般对话的区别。明确的短跟进可以接续同一会话的任务，其他输入重新判断。读者背景只来自任务中明确的读者要求，每一条有独立证据；不推断用户本人身份。`analysis.contexts` 使用各自的会话分母，推荐从同一场景的画像取证。

上下文中的 `language` 指交付语言。明确的英文写作要求在中文短跟进中继续保留，附带 `language_evidence_id` 和 `language_basis`；没有明确要求时，消息语言只是暂定依据。推荐的 `context_evidence_ids` 同时保留语言和读者来源，筛选不能改变这些事实。

`task_id` 记录这组跟进最初的请求。新主题重新开始；短跟进、问答回执和同一文件引用可以接续。说明修改必须与先前交付属于同一组，不把新任务的“没看懂”当作对旧交付的反馈。文件引用只比对路径后缀，不能据此评价未读取的正文。

尚未交付的同轮补充按任务累积，保留每条要求的来源；明确改变篇幅上限时替换对应对象的限制，取消时移除该对象的待执行限制，交付后结束累积。原始要求仍保留为历史证据，不用它继续约束已经取消的交付。文件交付与附带正文分开标记，同次连续回复中正文可出现在链接前后；截断前保留结构线索。这只能识别正文出现，不能确认完整性或质量。

`content.py` 只负责写作对象与篇幅：摘要、正文和首层回复各自保留限制，顿号分隔的要求也独立绑定。同次连续交付的多条回复合并计算，人工插入的分隔符不计字数。正文限制需要可识别的正文标记；边界缺失时保持未知。折叠标题和默认展开内容计入首层，明确限制正文时则核对正文全部内容；代码围栏里的标签保持字面含义。

导入时保存完整消息的篇幅统计，再截断展示文本。只有截断片段时给下界，不猜后面的内容；不完整的折叠标签可能改变可见范围，因此不据此前缀断言超限。没有明确摘要边界时只测首段，并标为代理值。它不判断数学正确性，也不替读者评分。分析 JSON 的 `schema_version` 为 `1.8`，包含独立画像、瓶颈案卷、标准化示例与改写审计。

`portrait.py` 在资源匹配前生成 `profile / bottleneck_details / normalization`。CLI 把它们独立保存，按场景筛选时保留原始任务证据。任务数、会话数、消息数采用不同去重单位；协作密度只作描述。具体推导见 [画像说明](../modules/analytics/profiling.md)。

结果分两层：`summary / findings / bottlenecks / next_step` 面向读者，`details` 留给开发者复核。建议里保存来源版本、匹配证据与试用方法，当前统一标为效果未测。

资源获取在 `resource_fetch.py`，只有显式执行 `catalog-refresh` 时联网。它读取公开 Markdown 与仓库元数据，校验固定提交和 Git blob 哈希，再原子更新本地缓存。`catalog.py` 只接收来源校验字段；适用场景和能力标签仍由本地目录决定，外部文档不能改写分析规则。缓存损坏时退回随代码提供的固定版本，并标明状态。

## 接口

| 路径 | 返回什么 |
| --- | --- |
| `GET /health` | 版本与导入规模 |
| `GET /v1/projects` | 项目 ID、名称和会话数（main / 全部 kind），默认隐藏无会话项目 |
| `GET /v1/sessions` | 会话列表，含模型与 kind，可按项目与 kind（默认 main）筛选 |
| `GET /v1/sessions/{id}/events` | 可分页回看的统一事件 |
| `GET /v1/analysis` | 易读结果与分析细节，可按项目、模型、时间筛选 |
| `GET /v1/catalog` | skills 与其他公开资源的固定版本、来源状态 |
| `GET /v1/evidence/{id}` | 一条建议引用的原始事件 |
| `POST /v1/evaluation` | 对输入文本做场景检查，不写入画像 |

`audience=user` 与 `audience=developer` 选择报告读者。用户版先给具体核对项；开发者版补充分母和推荐引用方式。事实与推荐相同。`before` 使用带时区的 ISO 时间；没有对应数据时返回同字段的无数据状态，不沿用全局画像填充。

`scene=math_explanation` 等筛选保留相应请求之后的工具和响应，便于核对完整结果。CLI 对应 `report --scene math_explanation`。其他场景为 `developer_report / document / coding / conversation`。

## 数学在这里解决什么

**并发计时。** 工具记录的起止用 call ID 配对。两次调用如果都覆盖同一秒，这一秒不能算两遍；按开始时间排序，合并重叠区间即可，复杂度为 `O(n log n)`。缺结束或时间倒退的调用保持未知。日志跨度仍不等于 CPU 时间、人工投入或完整交付时间。

**有限样本。** 对某个要求，n 是有真实用户消息的会话数，k 是出现过该要求的会话数；同一会话说十遍仍只给 k 加一。附带 Wilson 参考区间，避免只展示 k/n 显得很确定。相关会话不满足独立二项样本的假设，因此这个区间仅供参考，不能证明长期稳定；后续先补任务分组与语义核验。

首版没有足够的验收标签，不能估准用户理想转移分布 p，或声称某个 skill 降低了 p 与 q 的距离。三份建模方案提供思路；其中待验证的假设与建议不当作已实现能力。

## 评价如何隔离

`evaluation.py` 检查文字中的明显问题，`pipeline_eval.py` 在独立临时目录中构造 Codex 日志，调用正式导入、分析和推荐。输入生成器只接收虚构的步骤，不接收预期标签；先产生结果，再比较 `data/pipeline_cases.json` 的标签。正常数据库无需打开。

指标分别统计画像维度、瓶颈、资源与读者的误报和漏报，并验证证据引用及条件删减。若没有预测出的正例，precision 保持未知，不以“什么都不推荐”换取满分。当前对照集用于开发规则，不能当成独立人类评分。

`reader_eval.py` 生成独立评审目录，冻结同一事实下的两种表达、隐藏版本名、交换展示顺序，并汇总已有评分。正文或映射变化时拒绝混用旧表，未填写保持未知；读者声明的验收仅适用于该批案例。两个读者命令都在打开历史数据库之前返回，评价不会变成画像证据。
